# Floating-point portability checklist

**Purpose.** The caller must write the same bytes for the same input on every machine it runs on: macOS and Linux, arm64 and x86_64, two cores and sixty-four. Floating-point code breaks that in ways no ordinary test sees, because each machine is self-consistent: its own runs repeat exactly, and only a comparison across machines shows the difference. This checklist holds the lessons of the portable-float work of September 2026 (`doc/devel/implementation_plans/portable_float.md`, reports `doc/devel/reports/implementations/portable_float_*.md`).

**What was found, so the rules below have a size.** On 2026-09-13 a score table computed with `powf` and `ln` came out two units apart in the last binary place on macOS and on Linux, which flipped a tie and measured a repeat tract a base longer on macOS. The same parameters file fitted on the two platforms differed in 7 of 574 lines. And a fit of one small cohort wrote three different files at one, four and eight threads, because its floating-point totals were split and joined according to the pool's width.

**Triggers.** Any `f64`/`f32` arithmetic in scope whose result reaches output: a written number, a comparison that decides a call or a filter, a fitted parameter, a sort key. In particular: calls to transcendental functions (`ln`, `exp`, `pow`, `log10`, `log1p`, `expm1`, trigonometric, hyperbolic, `cbrt`, `hypot`, `lgamma`); `const` or `static` values computed from them; parallel code (`rayon`, threads) that sums, folds or reduces floats; iteration over hash maps feeding float accumulations; tests that compare floats against recorded answers.

**Skip when.** The scope has no floating-point arithmetic, or its floats never reach output (timing, progress reporting, logging of durations).

## Rules

- **Transcendental functions go through `crate::float`, never std's methods.** `f64::ln`, `exp`, `powf` and the rest call the operating system's maths library, and IEEE 754 does not require those to round correctly. Measured on arm64: macOS's library and Linux's glibc disagree on about one argument in 540 to 2,700 for `exp` and `powf` (A2 report). glibc on x86_64 also picks between builds of `exp` and `log` at start-up, with and without fused multiply-add; that was not measured. `crate::float` computes them in Rust (the `libm` crate, pinned exactly in `Cargo.toml`), so every target gets the same bits. `clippy.toml` refuses the std methods.
  - **Blocker:** an `#[allow(clippy::disallowed_methods)]` in `src/` outside `src/float.rs`'s own tests, or a call that reaches the platform library another way — `extern "C"` declarations of `exp`/`log`, or a dependency's float helper that calls std (`statrs`; `num_traits::Float::ln` on `f64`, whose implementation calls std's).
  - **Nit:** a `libm` function called directly outside `src/float.rs` and `src/genetics.rs` (`lgamma`). It is portable — `libm` is Rust — but it bypasses the one module whose tests pin outputs to bits; route it through `crate::float`.
  - **Major:** a function the scope needs that `crate::float` lacks, added as a local helper instead of to `src/float.rs` with its pinned-bits unit test *and* a `clippy.toml` entry. After adding an entry, `scripts/check_float_ban.sh` must pass: clippy ignores a misspelled path without a word.
  - `sqrt`, `abs` and `+ − × ÷` are rounded exactly by IEEE 754 and are portable; `min`/`max`/`clamp` involve no rounding. Rust never fuses a separate `*` and `+` into one operation, so `target-cpu`, LTO and `codegen-units` do not change scalar float results. `mul_add` is required to round exactly too, but on a target without the instruction std calls the platform library's `fma`, and the project has no call to it (A1 inventory): a new one needs a note on which targets were checked. `powi` is **not** portable even though std's run-time loop is exact: with literal operands the compiler folds it using the build machine's `pow`. Use `float::powi`.
- **Constants computed from transcendental functions are a platform question too.** A `const` or a literal expression such as `(0.01_f64).ln()` may be computed by the compiler on the build machine. Through `crate::float` it is libm's own arithmetic and portable. When converting a constant moves a recorded answer, the project rule (plan §8) is to write it as its old bits — `f64::from_bits(0x…)` with the value in a comment — **and** add a test tying those bits to `float::ln` (or whichever function) within one step. A written-out constant without that test is **Major**: nothing notices when the formula it stands for changes.
- **Parallel floating-point totals must not depend on the pool's width.** A float sum's last bits depend on where it is split and in which order the parts are added. Two patterns are defects (**Major** when the total reaches output):
  - chunk or batch sizes derived from `rayon::current_num_threads()`, `available_parallelism()` or a `--threads` flag, when the chunks' floats are summed;
  - `par_iter().sum()`, `.reduce(…)` or `.fold(…).reduce(…)` over floats, whose tree of joins rayon chooses at run time. (`fold_chunks` yields per-chunk results in order and is deterministic when collected; the defect is a `.sum()` or `.reduce()` after it.)

  The fix: fixed-size chunks (a `const`), and a join order that depends only on the number of chunks — results collected in index order (`collect::<Vec<_>>()` preserves it) and added serially, or a tree of `rayon::join` split at fixed points with the right half added to the left, which holds only one partial total per level (`parameter_estimation::joint::fit`'s expectation pass). Integer totals are exact and may reduce in any order. **Test:** run the computation at one thread and at several (`rayon::ThreadPoolBuilder::new().num_threads(n).build()?.install(…)`) over data that spans **several chunks** — one chunk has nothing to join, so it cannot catch a `reduce` — and assert the same bits. `fit.rs`'s `a_census_of_many_chunks_fits_to_the_same_bits_at_any_pool_width` is the model.
- **Hash-map iteration order must not feed a float accumulation.** std's `RandomState` seeds differ per map and per process, and `ahash` seeds per process, so a sum over `.values()` can change its last bits between runs. Sort the keys, or use `BTreeMap`/`IndexMap`. **Major** when the total reaches output.
- **No reordering licences where output must be portable.** `f64::algebraic_add`/`algebraic_mul` and the rest let the compiler reassociate by the vector width it targets, which differs between an x86_64 AVX2 build, a NEON build and a debug build. **Major** in code whose results reach output. The portable way to get a vectorisable float sum is a fixed number of lane accumulators written in the source — for example `[f64; 8]` updated over `chunks_exact(8)` and combined in a fixed order — whose order does not depend on the target. (A fixed-size chunk summed left to right is deterministic too, but it is still one serial chain and does not vectorise; it buys thread parallelism, not SIMD.)
- **Tests compute expected values with `crate::float`, not std.** An expected value from std's `ln` beside code using libm compares two libraries and fails on one platform only. Where a test compares against answers recorded by another library (the deleted older caller's glibc numbers), a bit-for-bit comparison will fail after any library change: compare probabilities within a stated number of representable steps (`ulps`), and keep *decisions* — which record is dropped, which genotype wins, convergence — exact.
- **A near-tie is a portability hazard, and it has a signature.** A value that sits almost exactly halfway between two `f64`s (the flat-gap aligner's `ln(0.01)`) rounds differently in different libraries, and a score built from it can tie another. Where a comparison decides output (`>` between two likelihoods, a `max_by`), ask whether equal-by-construction ties are broken by an explicit, deterministic rule (index order) rather than by which side's last bit happens to be larger.
- **Portability tests must look at numbers written in full.** Calls rarely show a one-unit difference when the parameters are the same: with default parameters, over 160 regions, macOS and Linux wrote identical VCFs even with the platform library in place, while their fitted parameters files differed. (Each platform calling with its own fit did differ, in 46 of 6,735 records, one of them in QUAL.) A test meant to guard portability must digest something written at full precision — the parameters file — and it must be shown to fail on the tree without the fix, on two platforms, before it is trusted. A digest test whose checksum is the same with and without the defect is **Major**. `cli::cross_platform_digests` is the model.
- **State what was not covered.** Findings about portability name the platforms actually compared. arm64 macOS and arm64 Linux agreeing says nothing yet about x86_64 glibc; CI's Linux runner is the only x86_64 evidence.

## Evidence a finding needs

A portability finding is **Needs verification** until it has one of: a unit test failing on one platform and passing on another; a digest compared across two machines or two pool widths; or, for a std call, the call site and the argument range, with A2's per-function disagreement rates (`doc/devel/reports/implementations/portable_float_A2_libm_vs_std_2026-09-14.md`) as the size.
