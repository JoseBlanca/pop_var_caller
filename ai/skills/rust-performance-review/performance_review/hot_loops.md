# Hot loops & codegen checklist

**Purpose.** Surface inner-loop patterns that block autovectorization, force redundant bounds checks, or otherwise leave compiler optimizations on the table.

**Triggers.** Tight numeric loops, byte / bit processing, slice indexing, generic code in a hot path, dynamic dispatch where static would do, regex / parse loops.

**Skip when.** Code is not numerical or per-record processing in performance-relevant call paths. If dispatched anyway, write `No findings.`

## Rules

- **Iterators are zero-cost most of the time.** Idiomatic `iter().map(...).filter(...).sum()` compiles to the same code as a hand-written `for`. Do not file findings rewriting iterator chains as index loops without a measurement showing the chain hurts. Known exception: `Iterator::fold` has historically optimized worse than the equivalent `for` in some shapes — file at Likely only with a benchmark.
- **`copied()` over `cloned()` for `Copy` types.** `iter().copied()` lets LLVM emit register copies; `cloned()` goes through the `Clone` trait machinery, which is the same for `Copy` types but blocks some optimizations.
- **Bounds checks: avoid by structure, not by `unsafe`.**
  - `chunks_exact(N)` over `chunks(N)` removes a per-iteration tail check and unlocks autovectorization.
  - Iterators (no indexing) eliminate bounds checks the compiler cannot prove redundant.
  - A leading `assert!(idx < slice.len())` (or `assert_eq!(slice.len(), N)`) hoists the bounds check out of the loop body — counterintuitively, more `assert!`s can be faster.
  - `unsafe { *slice.get_unchecked(i) }` is the last resort, requires a `// SAFETY:` comment, and must be paired with a benchmark that proves the win.
- **Autovectorization needs the compiler's confidence.** It vectorizes when the loop body is straight-line, the trip count is known or bounded by `chunks_exact`, the data is contiguous, and there are no data-dependent branches. Filed: a tight numeric loop with an `if` inside that could be a `select` (e.g., `if x > 0 { acc + x } else { acc }` → `acc + x.max(0)`); non-`#[inline]` helpers preventing inlining of the loop body. Cross-reference: `methodology.md` on `target-cpu` — autovectorization to AVX2/AVX-512 needs the right target.
- **Float reductions do not autovectorize even when everything above is satisfied — restructure them.** IEEE-754 addition is not associative (`(a + b) + c` can differ from `a + (b + c)` in the last bits), so the compiler must keep an `f64` sum, dot product, or log-likelihood accumulation in strict left-to-right order: one serial add per element, no SIMD lanes, no independent accumulators. The same loop over integers vectorizes freely. The gap is large — in the pythonspeed.com benchmark over one million `f64` values, the naive sum took 563.1 µs against 144.5 µs for pairwise summation (and 595.2 µs against 151.9 µs for the same sum over `i64`, which vectorizes), and a sum-of-squared-differences dropped from 4.5 instructions per value to 1.0 (628.7 µs → 371.1 µs). Fixes, in order:
  - **On stable today: make the reordering explicit in the source.** Split the reduction into independent partial accumulators — chunked/pairwise summation: sum fixed-size chunks into separate accumulators, combine the partials after. The compiler may then vectorize each chunk, because the source no longer specifies one serial chain. Accuracy improves rather than degrades: pairwise summation's worst-case rounding error grows with the logarithm of the element count, naive left-to-right with the count itself.
  - **Now on stable: `f64::algebraic_add` / `algebraic_sub` / `algebraic_mul` / `algebraic_div`** (and the `f32` forms). These license reassociation per operation — scoped to the call site, unlike a global fast-math flag, and with no NaN or infinity assumptions — which makes them the *first* fix to reach for here, ahead of the multi-accumulator restructuring above. They were behind the unstable `float_algebraic` feature until the pin moved: verified 2026-08-25 by compiling all four under the repo's pinned 1.98.0, which succeeds where 1.97.1 gave `error[E0658]: use of unstable library feature`. Prefer them when the loop is a plain reduction; keep manual chunked accumulators where the *accuracy* of pairwise summation is also wanted, since `algebraic_*` only permits the reordering, it does not choose a better one.
  - **Caveat for the measurement plan:** any reordering changes results in the last bits, so a byte-identity check over emitted likelihoods or QUALs will flag the change. The plan must state the accepted numeric tolerance and compare within it — noting that for summation the reordered result is the *more* accurate one.
- **Manual SIMD is rarely the right answer; fix what blocks autovec instead.** If a loop is a data-parallel map over a contiguous array (element-wise arithmetic, bit-packing, Phred-score conversion on a long slice), confirm with `cargo asm` that autovec is already happening under the configured `target-cpu`. If it isn't, the cause is almost always algorithmic — data-dependent branches, non-unit strides, banded indexing, variable-length output per iteration — and reaching for `std::simd` / `wide` / intrinsics won't fix that, it will just bury the same shape in lane-masking code. File a manual-SIMD finding only when (a) the profile shows the loop owns meaningful self-time, (b) the shape is genuinely vector-friendly (regular strides, no early exits, homogeneous output), and (c) `cargo asm` proves autovec is blocked by a compiler limitation rather than the algorithm. Otherwise: the loop is not a SIMD problem, and the right fix lives in another category (data layout, allocation, or coarser parallelism with rayon). When a finding does clear all three bars, the fix cannot be `std::simd` on this repo's pinned stable toolchain (it is nightly-only); the safe candidates are `fearless_simd` (safe API, runtime feature detection, v1.0 planned September 2026) or `wide`. On this project's aarch64 targets NEON is in the baseline, so compile-time NEON suffices and runtime dispatch buys little.
- **`#[inline]` is a hint, not a free win.** Apply when (a) the function is in another crate and called from a hot loop (LLVM cannot cross-crate inline without LTO) or (b) it is small and called many times. Mark single-call helpers `#[inline(always)]` only with a benchmark; over-inlining bloats the icache.
- **Cold paths get `#[cold]`.** Error formatters, panic helpers, slow paths inside a fast-path function — `#[cold]` improves branch prediction layout and keeps the cold body out of icache. The `#[cold]` attribute is the closest stable equivalent to `likely` / `unlikely` (the intrinsics are nightly-only).
- **A branch on unpredictable data in a hot loop is a candidate; a branch on predictable data is free.** A correctly predicted branch costs about one cycle; a mispredicted one 15–20. Predictability is a property of the data, not the code: in the greyblake.com filter benchmark, the identical loop over the identical million `f64` values ran 4.5× faster sorted than shuffled (0.93 ms vs 4.15 ms), and the shuffled cost peaked at 50 % selectivity (3.94 ms) — where the predictor is wrong half the time. Per-read quality gates and pileup-column filters branch on data-dependent predicates, but real data is often runny or heavily skewed rather than 50/50-random — measure the predicate before assuming it mispredicts.
  - **The branchless filter: always write, conditionally advance.** `out[n] = x; n += keep(x) as usize;` writes every element and lets the cursor overwrite rejected ones. No branch, so cost is flat across selectivity (1.02–1.11 ms from 1 % to 99 % keep in the same benchmark) — but it *loses* where the branch predicts well: at 1 % keep the branched loop won, 0.59 ms to 1.09 ms. File only with (a) profile evidence the loop is hot and (b) evidence the predicate is unpredictable — the article itself states that precondition.
  - **Evidence without a branch-miss counter** (this machine has none — see `profiling_environment.md`): run the same loop on the same values sorted vs shuffled — bytes and work are identical, only predictability differs, so the gap is the misprediction cost. Count the predicate's true/false runs on real data to see how far from 50/50-random it is. Or run `valgrind --tool=callgrind --branch-sim=yes` for deterministic simulated mispredict counts (comparative between two variants of a loop, not absolute rates).
  - The cheaper first-line fixes stay first: turn the `if` into a `select`-shaped expression (`x.max(0)`, `if` as a value), and move genuinely rare cases behind `#[cold]`.
- **Static dispatch in hot loops.** `fn f<T: Trait>(x: T)` (monomorphizes) over `fn f(x: &dyn Trait)` (vtable indirection) when the type set is closed and the call is in an inner loop. Cost: more codegen, possible icache pressure. File only when a vtable call is on the per-record path.
- **Default `HashMap` hasher is slow for non-adversarial workloads.** `std::collections::HashMap` uses SipHash for HashDoS resistance; for internal maps with trusted keys, `rustc_hash::FxHashMap` (or `ahash::AHashMap`) is faster. Use the default for any map keyed on data from outside the process; switch to FxHash for internal maps where the keys are integers or short owned types and the gain is benchmarked.
- **`HashMap::entry` over double lookup.** `if let Some(v) = m.get(k) { ... } else { m.insert(k, ...) }` does two hashes; `m.entry(k).or_insert_with(...)` does one.
- **Avoid recomputing in tight loops.** Hoist invariants. `Regex::new` inside a loop recompiles per iteration; `s.chars().count()` is `O(n)`; allocations in the closure passed to `map` show up at scale.
- **`format!`, `write!`, and `Display::fmt` are not equivalent.** Inside a hot serializer, write directly to a reused `String` or `Vec<u8>` with `write!(buf, ...)` (and do not `unwrap` the result if the writer is `String` or `Vec<u8>` — both are infallible). Cross-reference: `allocations.md` on `format!` allocating a fresh `String`.
- **Match on bytes for ASCII parsers.** `match b { b'A' => ..., b'C' => ..., ... }` over `match c { 'A' => ..., 'C' => ... }` for ASCII-only protocols (VCF, BED, FASTA): byte matches lower the trailing UTF-8 decoding step out of the loop.
