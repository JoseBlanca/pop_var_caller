# Floating-point portability checklist (performance)

**Purpose.** A speed-up that changes the caller's output on some machines is not a speed-up; it is a correctness change with a benchmark attached. The caller must write the same bytes for the same input on macOS and Linux, arm64 and x86_64, at any thread count (`ai/skills/rust-code-review/code_review/float_portability.md` holds the correctness rules; read it too). This checklist covers what a *performance* change does to that guarantee, and how to measure the cost of keeping it. The lessons come from the portable-float work of September 2026 (`doc/devel/implementation_plans/portable_float.md`, reports `doc/devel/reports/implementations/portable_float_*.md`).

**Triggers.** A proposed change to floating-point hot code: reordering or splitting a sum, changing chunk sizes, parallelising a float accumulation, replacing a maths function with a faster one, changing `lto`/`codegen-units`/`target-cpu`, or benchmarking code that calls `crate::float`.

**Skip when.** No floating-point value on the changed path reaches output.

**Note on overlap with the correctness review.** The rules here produce rejections, not Hot-path or Likely findings: a proposal that makes output depend on the machine is refused whatever it saves. File the finding here with its measurement plan, and route the portability question through the code review's `float_portability` category for the correctness call.

## Rules

- **Every proposal states its effect on output bits, and on which machines.** Three answers are acceptable: *none* (shown by a digest before and after, e.g. `cli::cross_platform_digests` and `scripts/promote_ng_oracle.sh`); *moves once, the same on every platform and pool width* (shown on two platforms and two pool widths, with the moved lines explained); or *moves differently on some machines* — which is a rejection, not a trade-off.
- **Never make chunk sizes depend on the thread count, and never join float totals in an order the pool chooses.** A fit of one small cohort wrote three different parameters files at one, four and eight threads for exactly this reason. Chunk with a `const` size and join the chunks' totals in a tree fixed by the input's length — halve the chunk list at fixed points, compute the halves with `rayon::join`, add the right half's totals to the left's (`parameter_estimation::joint::fit`'s expectation pass). A `par_iter().sum()`/`reduce` over floats is a portability defect whatever it saves. **The shape has a speed side, measured on the joint-fit bench against the thread-sized chunks it replaced:** 16,384-position chunks left the small SNP/indel cases on one core; 2,048-position chunks computed in fixed batches of 64 and added in order made those cases 47–56% slower (three unequal chunks for four threads) and the real fit 2 to 7% slower in three macOS rounds (not explained; waiting for each batch's slowest chunk is a guess); the fixed join tree over 256-position chunks was within about 2% on every case. Measure a small and a large input before choosing.
- **`f64::algebraic_*` is not a portable fix.** It lets the compiler reassociate by the target's vector width, so an x86_64 AVX2 build, a NEON build and a debug build may sum differently. The portable way to get a vectorisable float sum is a fixed number of lane accumulators written in the source — for example `[f64; 8]` updated over `chunks_exact(8)`, combined in a fixed order. A fixed-size chunk summed left to right is deterministic but does not vectorise. The `hot_loops.md` rule on float reductions defers to this one.
- **Build settings do not move scalar float results in Rust.** rustc never contracts a `*` and a `+` into a fused multiply-add, so `target-cpu`, LTO and `codegen-units` leave scalar results alone; only `algebraic_*` code and target-dependent chunking are exposed. `mul_add` on x86_64 without the FMA feature becomes a call to the C library's `fma` — exact, but slow.
- **Do not swap `crate::float` back to std for speed, and do not call around it.** The platform library is faster — on arm64 Linux, libm's `exp` takes 1.3 to 2.1 times as long per call as glibc's on the arguments the fit passes (the two are level past underflow), and `powf` about 4 to 5 times (A2 report) — but it is the source of the disagreement. A faster function must be written in Rust inside `src/float.rs`, pinned by unit tests to bits, and measured on the whole run: it moves output once, the same everywhere, and that move is part of the proposal.
- **Know what the portable maths costs before proposing to win it back.** Measured on four tomato samples at about 3× (`portable_float_B7_measurements_2026-09-15.md`): the parameter fit became 27% slower on macOS and 29% on Linux; `call-from-psps` 1.7 to 2.0%; the joint-fit bench 7 to 46% by case, most at one sample. About 20% of the unchanged fit's CPU was `exp` and 10% `ln` (A3 profile, macOS).
- **Profile with the release profile's link-time optimisation.** `crate::float` is `#[inline]`, but the `libm` crate's function bodies inline into the caller only under LTO; the `profiling` and `soak` profiles set `lto = false` and should be expected to show more time in libm than a release build spends there (not measured).
- **Measure small differences interleaved, with the load logged.** A 30% effect disappeared under another application's load (one unchanged fit took 496 s against 280–288 s on a quiet machine). The design that survived: run the two builds back to back in every round, alternating which goes first; log the host's load every 20 seconds with each run's start and end (a Linux VM cannot see the host's load); run benches of both trees in the same session in the order A, B, B, A. A difference of about 1% between two builds can appear in either direction from the binaries differing at all: in one session `generate-psps` was 0.8% slower on macOS and 1.0% faster on Linux.
- **A bench that draws its data with transcendental functions may time different data in two trees.** Check before comparing: hash the drawn input in both trees, on each platform compared (the joint-fit bench's draws were shown identical in both trees on macOS; Linux was not checked).
