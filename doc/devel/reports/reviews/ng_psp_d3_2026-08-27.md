## 2. Verdict

**Request-changes. One Blocker, seven Majors, three wrong numbers — and the Blocker is the defect
the commit says it fixed.**

**A refused stream did not end.** `fail` set no terminal state; what stopped a refused reader was
its next read hitting the end of the source, which holds only while the whole file fits in one
16 kB fill. Past that the reader read on from wherever the source stood, took four arbitrary bytes
for a block length, and carried on. Measured over a plain `&[u8]` — the exact shape every
committed test uses — on a 69,769-byte file with one bit flipped: **refused after 129 records and
then handed back 3,585 more.** On a smaller file: refused after 5,980 records, handed over 5,681
more, and **ended cleanly**. That is a damaged file reported as damaged and then read as though it
were not, and it contradicts arch §4.1, `fail`'s own doc, the commit message, report §5 and the
project status — all of which list it as a fixed survivor. **Four of the five agents found it
independently.** The mutant died on the fixtures' size.

**The reader itself is otherwise sound under 1.47 million fuzzed inputs**: no hang, no panic, and
nothing allocated from a declared length. That is the property the whole error design exists for
and it holds.

## 4. Top 3 priorities

1. **B1 — a refused stream does not end**, and hands back thousands of further records.
2. **M1 — a block whose length prefix over-declares is unguarded**, so a two-block file reads
   back as one with records from a block nobody asked for.
3. **M2 — `buffered_bytes`, the number Milestone H4 measures against the 500 kB budget, is pinned
   by nothing**: a stub returning zero passes every check the module makes.

## 5. Findings

### Blocker

**B1: [block.rs:1515](../../../../src/ng/psp/block.rs) — `fail` does not end the stream; "finished" is a side effect of emptying one buffer**
**Categories:** reliability, errors, refactor_safety, extras, smells — **four agents, five
checklists.** **Confidence:** High. Measurements in §2. There is no terminal state:
`BlockCursor::between_blocks()` means both *before the first block* and *abandoned after a
refusal*, and the type cannot tell them apart. Milestone F hands this reader a seeked `File`,
where a file larger than one read chunk is the ordinary case.

### Major

**M1: [block.rs:1407](../../../../src/ng/psp/block.rs) — a block over-declaring its compressed length is unguarded**
**Categories:** reliability, errors, smells. Dropping `|| self.cursor.compressed_left > 0` leaves
66/66 green, and a file whose first block's length covers the second reads back as **40 good
records** instead of being refused. Only the opposite direction was tested.

**M2: [block.rs:1200](../../../../src/ng/psp/block.rs) — `buffered_bytes` is asserted by nothing**
**Categories:** reliability, smells, extras — **three.** A stub returning `0` passes all 66; so
does one dropping the read chunk. The only assertion is one-sided (`most_held <= budget`).

**M3: [block.rs:1331](../../../../src/ng/psp/block.rs) — the retry arm has one witness**
**Categories:** refactor_safety. Making the arm panic showed five of 66 tests reach it; putting
spec §8's exact defect into it — advance the coordinate before pumping — failed **one**. The near
miss is the memory walk, which crosses the arm over 11,999 records and then discards what it
built.

**M4: no test uses a source that returns short reads or fails with `Interrupted`**
**Categories:** reliability, extras — **two.** Every fixture is a `&[u8]`, which returns
everything asked for and never fails, so `read_exactly`'s refill loop and the `Interrupted` arm
never run. Three mutations survive all 66; the sharpest **refuses a good file read slowly**.

**M5: [block.rs:1636](../../../../src/ng/psp/block.rs) — `Zstd` is the only variant spanning two instructions**
**Categories:** errors. A corrupt frame and a too-narrow window differ only in a 20-digit code;
resolved, they read "Restored data doesn't match checksum" and "Frame requires too much memory for
decoding". The test asserting the message claims "the message says both numbers" and it names
neither.

**M6: [block.rs:1407](../../../../src/ng/psp/block.rs) — `BlockHoldsMoreThanItDeclared` carries three faults and reports `bytes_left: 0` for two**
**Categories:** errors. A block whose declared length exceeds its frame refuses with *"a block
holds 0 bytes past the last record its head declared"*.

**M7: [block.rs:1107](../../../../src/ng/psp/block.rs) — `rolling_at` is per-block state outside the group the compiler enforces, and the doc says the opposite**
**Categories:** refactor_safety. Dropping its reset fails 8 of 66, so it is parse state, not
storage. And `BlockCursor::between_blocks` uses `..Self::opening(0)`, so a field added to the
cursor is `E0063` at `opening` only and `between_blocks` silently inherits whatever `opening`
chose — for a field that must differ between "not started" and "started", exactly the wrong
default.

### Minor and Nits

Twenty-nine between the five. Acted on: the buffer's shrink-back is asserted by a **substring** of
a `Debug` string, so `"163840"` contains `"16384"` and a ten-times-larger buffer passes; the
timings in `READ_CHUNK_BYTES` and `next_record_where` read as measurements of this reader and are
the prototype's, with nothing having timed `BlockStream`; the module doc still says "Two halves"
and *"nothing reads one back through a rolling buffer (Milestone D3)"* — **the exact debt the D2
review attached to the previous deferral, re-incurred in the commit that discharged it**; and
report §2.6 upgrades the D2 review's "did not object" into "judged the deferral right".

## 6. Out of scope observations

- **⚠ Spec §8 and spec §1.1 do not both hold on a corrupt file.** A **4,132-byte block drove the
  reader to hold 67,125,248 bytes** — 2,048× the 32 kB budget — because a psp block's inflated
  size is not bounded by its size on disk, and when no record can be parsed the buffer doubles
  until the frame runs out. §8 says a record larger than the buffer must make it grow and that a
  fixed maximum record size is not safe to assume; §1.1 puts an open sample at 500 kB. **Which
  gives is the owner's call** — raised at Checkpoint D.
- **No budget refusal exists**, so Milestone F4 cannot produce `PspReadError::WindowTooLarge`:
  `BlockStream::new` accepts 2^31 = 2 GiB, though `MAX_LOOK_BACK_WINDOW_LOG`'s own doc says that
  refusal "belongs to the reader that Milestone D builds".
- **Neither buffer size is reachable from the API**, though spec §4.4's own table makes the choice
  cohort-dependent (1.11 GB against 1.23 GB at 5,000 samples).
- **`StreamedRecord::record` is the first public *field* carrying a pipeline-stage type out of a
  `pub` peer module.** Milestone F is already named as the last cheap moment to lift the
  `psp` → `locus_generation` back-reference.
- **The existing loop guards count records yielded**, so a spin *inside* one call would hang the
  suite with no message rather than fail it.

## 7. What's good

- **1,473,500 fuzzed inputs, 0 hangs, 0 panics, and nothing sized from a declared length.** Three
  shapes: 700,000 damaged files, 700,000 damaged payloads recompressed so the reader meets a
  well-formed frame with damaged contents, and 13,500 lying block heads. The largest payload tried
  was 255,940 bytes, 15.6× the rolling buffer.
- **No block ever returned a record count other than the true one** across those 13,500 lying
  heads.
- **The per-block reset guard works as claimed**: a field added to `BlockCursor` is
  `error[E0063]` at its constructor, reproduced by two agents.
- **Every per-block reset that matters is covered** — refactor_safety removed each in turn and the
  suite caught all of them.
- **The code is correct on sources it has no test for.** One agent verified by probe that
  one-byte-at-a-time and interrupting sources read the right records; those are coverage findings,
  not defects.
- **The `block/` split is still right to defer**, and this time on the checklist's own terms
  rather than on a paraphrase of the previous review.
