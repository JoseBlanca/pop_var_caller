## 4. Findings

### Blocker

**B1 — a footer that puts the block index inside the header makes `append` truncate the header
away and report success. This is G3's Blocker, one operation over.**

`PspReader::open` bounds `index_offset` below by the four-byte head magic and nothing else. The
rule that relates the index to the header is **per entry** —
`(header_bytes..index_offset).contains(&entry.block_offset)` — and it is **vacuous on an empty
index.** So a footer saying `index_offset = 4, index_bytes = 0, n_blocks = 0` passes
`decode_footer`, the sections rule, the checksum, the per-entry rule and `open`. `append` then
truncates at 4 and writes on top of the stump.

**The step's own defence does not cover it**: §2.1 says "a file the reader would refuse must not
be extended", and the reader **accepts** this file. Reproduced in the main checkout on the
standard fixture:

```
PROBE size before = 3742
PROBE open: None                    <- PspReader::open accepts it
PROBE append: accepted
PROBE finish: Ok("WriteStats { records: 1, blocks: 1, bytes: 109 }")
PROBE size after  = 109
```

G3's fix added the trailer-side bound in `trailer.rs` and a test for the *index*-side bound —
**in `trailer.rs`, for the operation that does not truncate at the index.** The operation that
does was written one commit later without it.

### Major

**M1 — the seam test cannot tell the last record from the last block's first.** Both records it
offers precede *every* record in the last block, so it separates *seeded* from *not seeded* and
nothing finer. An implementation keeping the **first** record of the last block passed all 381
tests, and a record between the two — `contig 1:3002`, where the seam is `3401` — is accepted
under it. That is the shape G1's Blocker was.

**M2 — a compression level recorded in a shape this writer cannot read was silently ignored.**
`the_files_own_compressor` matched only `Integer`; a level recorded as `String("1")` or
`Float(1.0)` fell into the same arm as *absent* and the append wrote level-9 blocks into a file
claiming level 1. **That is the file §2.4 says must not exist, produced without a word** — and
§2.4's own sentence is that a setting recorded and then ignored is worse than one not recorded.

**M3 — a recorded level outside `i32` was reported as a level the file does not contain.**
`unwrap_or(i32::MAX)` mapped every out-of-range `i64`, positive and negative, to `i32::MAX`, so a
file recording −5,000,000,000 was refused for recording 2,147,483,647. It is the clamp
`BlockCompressor::with_level` exists to prevent, moved one function upstream. Nothing reached the
path: `unwrap_or(1)` left 381 green.

**M4 — nothing tested `append` on a psp with no records**, which is the one input where the
empty-index early return is the whole function. `finish` writes such a file whenever a sample has
no coverage, and `records()` documents it by name.

**M5 — `WriteStats`' field docs are false after an append.** `records` counts this writer's;
`blocks` and `bytes` describe the whole file. Measured: appending one record to the eight-block
fixture gives `WriteStats { records: 1, blocks: 9, bytes: 3790 }`. The rule lived in an inline
comment, a trade-off note and one test's message — not in the public doc a caller reads.

### Minor

- **`a_file_with_no_footer_cannot_be_appended_to` asserts `Reopen { .. }`**, which cannot tell
  `Incomplete` from `NotAnNgPsp`, `Damaged` or `Io` — G3's M2 again, in a test written after that
  finding was fixed.
- **"the last block is the only one read" is a cost claim with nothing holding it.**
  `records_from_block(n)` walks to the end of the file, so starting at block 0 gives the same
  answer while reading every block — 40 records instead of 5 on the fixture, and the whole file
  instead of one block on a real psp.
- **The interruption window is tested at one stopping point** where `replace_trailer` is tested at
  every one — and `append` is the more destructive of the two.
- **`push`'s destructure ends in `..`**, which is the one form the repo's refactor-safety rule
  argues against, and the error arms reach `self.spent` and `self.path` through `self` inside it.
- **The names.** `the_last_record_in` and `the_files_own_compressor` are noun phrases for fallible
  operations, and the second's noun is wrong: it takes a `&Header`, not a file.
- **The arch doc is stale a fourth time**: §1's tree still says `writer.rs – PspWriter: create,
  push, finish`.

### Nits

Two copies of "write a block and give it its index entry" now exist, `push`'s inline one and
`put_block`. `UnsupportedManifest`'s `Display` says the file "declares a manifest this writer
cannot honour" for a failure in `header.writer.parameters`, which is provenance and not the
manifest.

## 5. The author's own numbers

Three were wrong, all about this work:

- **"eight defects injected, eight caught"** — the table has **seven** rows. The eighth was
  removing the assertion itself, which survives by construction and was described in prose rather
  than counted.
- **"the same defect fails 74 either way"** — wrong. Measured here after the fixes: **82 failing
  with the assertion, 66 without**, so it accounts for sixteen. The conclusion — keep it — is
  better supported than the report claimed.
- **The code comment still carried F's "1 failing test to 7"**, measured on a suite a third this
  size.

381 against 373, 4,918 against 4,910, and eight tests added: all correct.

**And one sentence of the argument for not splitting `PspWriter` was wrong**: the
`Option<BlockBuilder>` is not what makes "finished exactly once" a type-level fact — `finish(self)`
is.

## 6. On the four design questions

1. **Not splitting `PspWriter` — right call**, with the correction above: the split is deferred
   into one function's borrow pattern, not refuted.
2. **`push`'s shape is sound**, `put_block` is neither dead nor inconsistent (`finish` still calls
   it), and the allocation it bought is real and measured.
3. **`the_last_record_in` and `the_files_own_compressor` are in the right homes, with the wrong
   names.** Worth recording as *good*: the loop is deliberately not `.last()`, which would swallow
   errors.
4. **`continuing_after` is the right shape and the right name, and `from_manifest` must not take
   the seed** — doing so would force the walk before the manifest check, reinstating the exact
   defect §2.2 describes. **But both of its documented claims were unasserted.**

## 7. What's good

- **No panic across 7,484 hostile mutants, and every refusal byte-identical.**
- **The per-block copy is measurably gone**, one allocation per block.
- **Checking the manifest before walking** — §2.2 — is the right order and the review confirmed
  the alternative reinstates the defect.
- **`the_last_record_in`'s loop is deliberately not `.last()`**, which would swallow the errors an
  iterator of `Result` carries.
