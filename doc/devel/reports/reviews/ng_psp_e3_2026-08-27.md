# Code Review: ng psp E3 — the chain ids' changes in the record head

**Date:** 2026-08-27
**Reviewer:** rust-code-review skill (orchestrator), eight category checklists across three
sub-agents, each in its own git worktree
**Scope:** commit `4f138292` on `ng-psp-encoding` — step E3, which changes production code in three
files and changes the file format
**Status:** Request-changes

---

## 1. Scope

- **What was reviewed:** the diff of one commit, the whole of `record.rs`, `block.rs`, `header.rs`
  and `chain_ids.rs`, and the implementation report, commit message and status entry, whose numbers
  were re-derived rather than read.
- **Deliberately out of scope:** the frozen production tree `src/psp/`; the two example targets
  that fail on a missing `ref.fa.repeats.parquet` fixture.
- **Categories dispatched:** all eight, paired onto three agents.

**What the three did.** **35 mutations** applied and run, **12,000,000 fuzzed inputs** across eight
seeds through the record decoder, and three independent traces of the writer's refusal paths.

## 2. Verdict

**Request-changes. Two Blockers, and the first is the previous step's Blocker one level up.**

**`read_record_head` applied the chain-id changes and only then bounded the body.** A body that
stops early is a `Truncated`, whose contract is *fetch more bytes and re-parse this record from its
first byte* — and `BlockStream` does exactly that, under a comment saying the restart resumes
*"against state this arm has not touched"*. It had touched it.

**All three agents found it independently**, and the measurements are worse than a refusal:

- **a well-formed file is rejected as damaged.** Over 1,999 records each naming twenty live reads,
  in blocks larger than the 16 kB rolling buffer, the reader refuses at record 149 with *"id 150,
  which is already live"* — the retry meets an arrival the first pass already applied;
- **and a record that only departs reads retries to `Ok` with the wrong set.** A departure is a
  *position* in the live set: the first pass shrinks it, the second resolves the same positions
  against the shrunken set and removes different reads. Measured, `[1, 2]` where the truth is
  `[1, 2, 4]` — no error, and every later record in the block composed against a set short by one.

**The suite could not see either.** Every fixture that reaches the retry path had empty chain-id
lists, so each record's changes were the two bytes `0, 0`, and applying them twice is applying them
never. The one test that provably retries — 37,209 restarts at a byte a read — walks records with
`chain_ids: Vec::new()`.

**The second Blocker is a coverage hole of the same shape.** A writer that named only the *first*
observation's reads passes all 4,770 library tests, because no psp fixture had ever put chain ids
on two observations. A record's observations are split by allele, by witness and by read group, so
a locus with two alleles from two lanes is four observations with the reads spread across them.

**The step's two design claims hold.** All three of `encode_record_starting_a_block`'s refusals
were traced and fire before either reset, `write_a_record` is infallible after them, and
`BlockBuilder` has no other path needing a rollback — a mutation that resets before the refusal is
caught. And the changes really do sit in front of `body_bytes`'s reach.

## 4. Top 3 priorities

1. **B1 — the changes are applied before the body is bounded**, so the retry a short read
   instructs is not a retry.
2. **B2 — only one observation's reads need be named** for the whole suite to pass.

## 5. Findings

### Blocker

**B1: [record.rs:1543](../../../../src/ng/psp/record.rs) — the live set moves before the record can still be refused**
**Categories:** errors, reliability, smells — **all three agents.** **Confidence:** High.
Measurements in §2.

**B2: [record.rs:1352](../../../../src/ng/psp/record.rs) — the writer may name only the first observation's reads and pass everything**
**Categories:** reliability. Confirmed independently: `.take(1)` on the observations leaves all
4,770 library tests green.

### Major

**D1: [record.rs:1487](../../../../src/ng/psp/record.rs) — `read_record_head`'s `&mut LiveSetReader` carries an undocumented "exactly once a record" contract, and the pairing that satisfies it is not exported**
**Categories:** defaults. The rule is written only in an inline `//` comment, which rustdoc does
not render; and `decode_the_body_of` is not in `mod.rs`'s re-export list, so the only route
available to an outside caller holding a head is `decode_record`, which parses it again.

**X1: [record.rs:525](../../../../src/ng/psp/record.rs) and [:1110](../../../../src/ng/psp/record.rs) — two surviving mutants on the new code**
**Categories:** extras. Nothing tests `further_in`'s re-basing — dropping it, or converting the
class the way `inside_a_bounded_body` does, both pass. And nothing tests the `ChainIdChanges` arm of
`skip_unknown_field`: replacing its arrival-count read with a constant passes.

**X2: [record.rs:3572](../../../../src/ng/psp/record.rs) — the malformed-input suite never carries a chain-id change**
**Categories:** extras. The same empty-fixture blindness as B1, seen from the other side.

**N1: [header.rs:246](../../../../src/ng/psp/header.rs) — the new variant's doc says the encoding "cannot be walked past by anybody" while the same commit walks past it**
**Categories:** naming, smells. `skip_unknown_field` measures and steps over one; what must never
be stepped over is the *head's* copy.

### Minor and Nits

Fifteen between the three. Acted on: `FieldReader::skip` is the one advancing method with no bound,
on a value that came out of parsing untrusted bytes, in a type whose doc rests on
`bytes_read <= bytes.len()` being total; `RecordEncoder::for_block` remains a second way to open a
block, called with a placeholder coordinate in the commit that removed the first one, while
`encode_record_starting_a_block`'s doc claims to be "the only way"; five docs still count four head
fields and a twenty-three-field manifest; `PerBlockState`'s doc still argues that the chain-id live
set belongs inside it, which is the placement this step did not take; `decode_record`'s doc still
argues it must not be two calls, after the commit made it two calls; and a header test still says
"that is not one of the six".

## 6. Out of scope observations

- **`next_record_where` returns `Option<Result<…>>` while carrying a `refused` latch**, so a
  refused stream and an exhausted one are the same value to a caller. Pre-existing.
- **`decode_the_body_of` is a verb phrase** where the module's other public functions are a verb
  plus a noun.

## 7. What's good

- **12,000,000 fuzzed inputs across eight seeds**, each under a deadline and a 2 GiB address-space
  limit, with the harness demonstrated able to abort: no panic, no hang, and **no allocation driven
  by a declared length**.
- **The header side is complete and correct** — the spelling, `ALL_ENCODINGS`, the parse match, the
  parameter check and the writer/reader round trip over every scheme.
- **`further_in` is right to preserve the class where `inside_a_bounded_body` converts it**, and
  the reasoning was checked rather than assumed: the chain-id parser is handed the rest of the
  record, not a bounded slice, so more bytes is exactly what helps.
- **`skip_unknown_field`'s new arm measures exactly what `encode_changes` writes.**
- **The writer's refusal ordering holds.** All three refusals fire before either reset, and the
  mutation that reverses it is caught.
- **Every figure in the report re-derived and holds.**
