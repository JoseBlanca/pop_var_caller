## 6. Findings

### Blocker

**B1: [writer.rs](../../../../src/ng/psp/writer.rs) — a lost block produces a valid-looking file**
**Categories:** reliability, errors (both agents, independently).

`BlockBuilder::push` swaps its buffers and reopens **before** returning the closed payload, so
once `PspWriter::push` holds it the builder will never hand it back. Reading its head, compressing
it and writing it can all still fail — and nothing marked the writer spent, so `finish` stayed
callable.

Measured, with a one-shot failure injected into `put_block` and the existing fixture pushed:
`finish` returned **`Ok`**. The file has a valid footer, a checksum-matching index, seven entries
that decode with ascending positions and offsets all landing on whole blocks — and **contig 0
jumps from position 1,001 to 3,001 with a thousand bases missing from the middle.**
`WriteStats.records` reported 40 against the 35 actually in the file.

A permanently-full device is safe: every later write fails, so `finish` is refused. **The
dangerous failure is the one that does not persist.** My own doc comment argued the opposite — "an
I/O failure here is terminal and is meant to be" — which holds only while the failure holds.

**B2: [writer.rs](../../../../src/ng/psp/writer.rs) — the index test never checked the index**
**Categories:** reliability, extras (both agents).

Shifting every entry's position 100 bases past its block's true head survived all twelve tests.
`every_index_entry_points_at_the_block_it_names` never inflated a frame or decoded a `BlockHead`;
**its doc comment claimed an assertion it did not make.** The contig half was caught only
transitively — forcing it to 0 breaks ordering, so `decode_index` refuses — so any error
preserving ordering, an off-by-one-block index most of all, was invisible.

### Major

**M1: the flush gap was closable here.** F3 recorded "no test here can make a real file's flush
fail" and routed it to H2. Linux's `/dev/full` accepts an open and fails every write with
`ENOSPC`; the fixture is well under `BufWriter`'s 8 KiB buffer, so nothing reaches the device until
`into_inner` flushes inside `finish` — pinning exactly that step. Verified both ways by the
reviewer, and now by me.

**M2: the compression level never reached the file.** `block.rs`'s own doc assigns recording it to
"Milestone F3" **by name**; F3 writes the header and did not. `append` must match bytes already in
a file and would have had no way to learn the level.

**M3: `create` silently truncates an existing finished psp.** Probed: a finished 3,715-byte psp
became a 3,109-byte header-only stump after a second `create` that was never finished, with no
error. The spec warns about the milder destruction in `append` and says nothing about this.

**M4: moving the readable-check after the writes survived every test** — and leaves a file ending
in the footer magic on disk from a `finish` that returned `Err`. By this module's own contract
that is a *finished* file, which is worse than the stump a killed run leaves.

### Minor

The readable-check omitted the index checksum, so the mutation computing it over the trailer
sailed through the guard (extras); `Option<BlockBuilder>` and the per-block `to_vec()` are one
problem with one fix, and this `expect` is **not** the class `count_one_more_record` tolerates —
that guards a field with a real `None` state, this one guards a field whose own doc says it is
always `Some` (idiomatic); `create` propagates `Header::encode`'s error without the path, and that
variant has no path field, so the likeliest `create` failure cannot say which of sixty samples it
was (errors); five `map_err` sites flatten typed causes into `String`, so `source()` returns
`None` (errors, smells); adding a variant to `BlockWriteError` compiles clean, absorbed by
`push`'s `other =>` arm into `RecordRefused`, whose doc enumerates exactly today's set
(refactor_safety); a fifth section between the trailer and the footer is caught by one assertion,
and only because that fixture has a non-empty trailer (refactor_safety); `finish`'s doc still said
durability was three steps while the code does two, with the explanation 50 lines below where a
docs reader looks (extras); `push`'s doc claim that "a refused record leaves the file exactly as
it was" does not hold for two of the three refusal classes (extras); `an_empty_trailer_is_legal`
asserts only a relation the guard already guarantees and passed under a mutation putting
`index_offset` a whole block short (reliability); and the naming set — `head_of`,
`check_it_is_readable`, `written`, `WriteStats`' three fields, `RecordRefused` (naming).

### The author's own numbers

**N1: "Twelve defects injected, eleven caught" — the table names ten defects and nine are
caught.** Every kill count in it is right; both totals are two too high, and the survivor is
called "the twelfth" when it is the tenth. Repeated in the commit message, the report and
`PROJECT_STATUS.md`. **This is the third milestone step running with a miscounted defect table**,
and the second in the same direction as F2's.

Everything else re-derived clean: 12 writer tests, 4,836 after and 4,824 before, 8 blocks at 1 kb
against 2 at 1 Mb with 2 the floor even at 100 Mb, and the `into_inner` claim **measured** with a
mock sink — after a successful `flush()`, `into_inner()` issues zero writes and returns `Ok` even
with the sink rigged to fail.
