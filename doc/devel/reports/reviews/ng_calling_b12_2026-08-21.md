## 6. Findings

### Major

**M1: `admit`'s overflow guard had no test, and the doc's reachability claim was about a different
caller.** **Category:** reliability. **Confidence:** High.

The guard panics when a table already holds 65,536 alleles. The submitted doc justified not
testing it as "unreachable in any real run — production keeps 6 alleles per record by default and
refuses to be configured above 16". Those caps are `DEFAULT_MAX_ALLELES_PER_RECORD` and
`MAX_ALLELES_PER_VAR_CAP` in `src/var_calling/per_group_merger.rs` — **production's frozen caller,
which ng neither shares code with nor may depend on.** `grep -rn "max_alleles\|MAX_ALLELES"
src/ng/` finds no cap in ng at all; the only hit repeats the same claim in `src/ng/types.rs`.

So in ng nothing but that guard stands between a pathological locus and a wrapped id. Measured:
with the checked conversion replaced by `len() as u16`, all six tests stayed green, and a probe
showed pristine panicking at 65,536 against the mutant returning `AlleleId(0)` — which *is*
`AlleleId::REFERENCE`. A wrapped id does not fail; it makes a discovered alternative *be* the
reference for the VCF's REF/ALT split and for the homozygous-reference genotype in the prior.

**M2: `ExpectedAlleleCopies::new` refused the empty vector and nothing else.** **Category:**
reliability, `errors` (convergent). **Confidence:** High.

A probe stored `[-1.0, NaN, inf, 0.7]` without complaint, and on the next line showed the
consequence: the derived `PartialEq` on `Vec<f64>` is not reflexive once a `NaN` is inside — the
value was unequal to its own clone. That comparison is the loop's stopping rule
(`spec/calling_em_loop.md` §6: the change in summed expected copies between passes), so one `NaN`
makes the test false forever, the locus runs to its pass cap, and it is emitted `converged: false`
with nothing naming the real defect. Two mutants that silently *repaired* such values — a clamp at
zero, a scrub of non-finites — both survived the suite.

The submitted test's own comment overstated its fixture: `[1.4, 0.6]` catches a round and a clamp
at 1.0, but not a clamp at 0.0.

**M3: the parallel-length contract was written in prose and enforceable nowhere.** **Category:**
reliability, `errors` (convergent). **Confidence:** High.

The doc said "entry *i* is allele *i* … nothing in either type can check that". A probe built the
mismatch in two lines — `alleles=2 copies=1` — with no complaint, and neither type had a `len()`,
so even a consumer that wanted to check by hand had to reach through two accessors.

**The two agents recommended different places for the check**, and that disagreement is the useful
part. `errors` wanted the constructor to take the table and `assert_eq!` on the lengths, which
subsumes the emptiness guard. `reliability` wanted `len()` on both types now and one `assert_eq!`
in B3's `LocusInference`, arguing that a constructor taking `&CandidateAlleles` "makes the copies
type depend on the allele table for no other reason".

**Resolved for the constructor** — see the fix-application report for the reasoning, and both
halves were taken: the constructor enforces it *and* both types gained `len()`.

**M4 (errors): the emptiness guard checked the property that could not produce a wrong answer.**
An empty copies vector panics at the first consumer that indexes; a copies vector of length 3
against a four-allele table reads downstream as a wrong cohort frequency with `converged: true`
beside it. Subsumed by M3's fix.

### Minor

- **Mi1 (reliability): `LocusKind`'s payload-carrying variant was untested.** The kind test covered
  `Generic` and `SsrBundle` only. A mutant that empties an `Ssr` locus's left flank inside `new`
  survived — and for a repeat tract the flanks *are* the read model's alignment anchor, so a
  dropped one is a wrong likelihood at every repeat locus with nothing panicking.
- **Mi2 (reliability): the out-of-range test used a one-allele table**, which is the one width at
  which its own comment's worse case — "returns a different locus's allele" — cannot happen. A
  mutant narrowing the id to a `u8` survived; on a 301-allele table it returned a real but *wrong*
  allele for id 256 and a present allele for one past the end.
- **Mi3 (reliability): `new` accepted a zero-length reference allele.** Verified by probe. ng's own
  `reference_bases` is documented as "one base for a candidate SNP, several for an indel, the tract
  for a microsatellite" — never empty — and the agent checked that this repository's VCF encoder
  does not reject an empty `REF`, so the failure mode is an unparseable record, not a crash.
- **Mi4 (reliability): no property test for the admit/lookup round-trip**, though `proptest` is a
  dev-dependency and step A1 uses it in the same file style. The three-allele fixture cannot
  separate a dense id scheme from any scheme agreeing at widths one to three — and width is the one
  dimension a discovery round moves.
- **Mi5 (idiomatic): `alleles() -> &[Box<[u8]>]` gave away the storage freedom the private field
  had just bought**, was the only route to the allele count, and made the file's own tests pay a
  `Box::as_ref` conversion twice.
- **Mi6 (idiomatic): the prune had no route through the API at all** — no `retain`, no `remove`, no
  `&mut` accessor — while being named twice as the reason the type owns its alleles.
- **Mi7 (naming): the module doc's headline justification was factually inverted.** It said four
  sibling modules "would have had to import sideways from each other, **which the tree forbids**".
  `module_layout.md` says the opposite: nothing forbade it, which is exactly why three architecture
  documents each had to write a no-import rule by hand, and the one folder is what makes those
  rules unnecessary.
- **Mi8 (naming): "the calling loop and the three things it drives" was followed by four items**,
  and the module doc opened on a step number rather than on what the module does.
- **Mi9 (naming): `push` named the `Vec` operation, not the domain event.** The architecture
  already has the verb — discovered sequences "enter `CandidateAlleles` through the same
  **admission** as selected ones".
- **Mi10 (naming): `get` was the vaguest name beside `reference()` and `alleles()`**, and its body
  spelled two unrelated `get`s in one expression.
- **Mi11 (naming): `ExpectedAlleleCopies` took the spec's *per-sample* term as the name of the
  *cohort sum*.** Both quantities are live and same-shaped — `calling_priors.md` has
  `cohort_expected_copies` beside `own_expected_copies` — and the prior's leave-one-out term is a
  subtraction of one from the other, so confusing them is a wrong prior rather than a compile
  error.

Also filed and applied: four terms carrying arguments before being defined (*the candidate step*,
*the merge's own table*, *row builder*, *the prior's seed*); `&[Box<[u8]>]` described as a "flat
view" when the arch reserves that phrase for `GenotypeTable`'s genuinely flat `Vec<u32>`; and
`kind` being public while `alleles` was private, which let a table be re-routed to another read
model after its alleles had been chosen by the right one.

### Nits

private field's doc repeated the type doc's argument; no single-allele fixture for the copies type;

## 9. What's good

- **20 mutations, 5 survivors, 0 no-ops, and each survivor proved to change behaviour** with a
  probe before being written up. The 15 killed covered the whole reference-at-zero family: empty
  seed, insert-at-front, id off-by-one, constant id, indexed lookup, clamped lookup, `reference()`
  returning the last allele, sub-sliced view, dropped assert, rounding constructor.
- **The private-field departure was judged on evidence, not taste.** All twelve mutations attacking
  the reference-at-zero invariant died against tests a public `Vec` would have made unwritable.
- **A wrong claim in the diff's own prose was caught and traced to its source.** "Which the tree
  forbids" was checked against `module_layout.md` and found inverted — the kind of sentence that
  reads as authoritative precisely because it sounds like a rule.
- **One agent flagged the weaker half of its own evidence**, noting that the narrowed-id mutation
  needs a table wider than 255 alleles, which no ng cap forbids but no real locus reaches.
- **The prune's absence was argued as better than the alternative**: inheriting `Vec::retain` free
  would be worse, because dropping allele *k* renumbers every id above it and stales every
  `AlleleId` and `Genotype` minted before it — so the method has to return the remapping.
