## 2. Verdict

**Request-changes.** Two Blockers and eleven Majors. **Both Blockers are the same defect met from
two directions** — a value the reader hands out that detonates in whoever asks it a question — and
neither was reachable by reading. Three of the diff's own claims were measured wrong, one of them a
number carried forward from C1's fixes after it had stopped being true.

**And one C1 finding was only half closed.** C1's Blocker was that the manifest and the codec could
drift; its fix pinned the field *names* longhand and the body's *bytes* longhand. Three categories
found independently that the declared **encodings** are pinned by neither: declaring a field an
8-byte float while the codec writes a variable-length integer passed all 97 tests, on the head's
fields and on the body's alike.

## 4. Open questions and assumptions

1. **Is a head declaring a body no buffer will hold `Truncated` or `Malformed`?** (B2's neighbour,
   M6.) Spec §8 refuses a fixed maximum record size — "the buffer has to grow rather than fail" —
   so `Truncated` is defensible; what was missing is any test saying so. **Resolved: `Truncated`,
   pinned, with the reasoning at the test.**
2. **Should the head's `non_reference_reads` be checked against the body?** It is derivable from
   the body the reader just built, and the disagreement that matters reads *low*. **Resolved:
   checked.**
3. **Does the offset base become a type now or at Milestone D?** Three categories priced the wrong
   base and all three said now. **Resolved: a type, and the encoder holds its own.**

## 5. Top 3 priorities

1. **B1 — a fault inside a body the head already bounded comes back as the *retry* signal.** More
   bytes cannot change the answer, so a streaming reader would grow its buffer for ever on one
   damaged record.
2. **B2 — a corrupt head can mint a region whose own length accessor overflows**, and the module's
   own test suite makes that call. `push` has the mirror hole and writes an unreadable record in a
   release build while returning `Ok`.
3. **M1 — the offset base is a bare `Position`, so the record's own start type-checks in its
   place**, and every wrong base is silent: measured, a writer handing each record its own start
   collapses a whole block onto one coordinate with no error anywhere.

## 6. Findings

### Blocker

**B1: [record.rs:1186](../../../../src/ng/psp/record.rs#L1186) — a body fault inside a bounded body is reported as `Truncated`, the class Milestone D fetches more bytes for**
**Categories:** errors. **Confidence:** High.
`read_record_head` hands the body a slice of exactly the declared length, so a field running off
*that* end is not a buffer that stopped early. Measured, each input run twice — once with the buffer
holding exactly the record, once with 4,096 further bytes appended, which is what a retry supplies:

```
head under-declares by one   exact -> Err(Truncated { field: "locus-kind", bytes_in: 76 })
                             grown -> Err(Truncated { field: "locus-kind", bytes_in: 76 })
```

**The retry is a fixed point.** The specs classify it the other way — spec psp_record_encoding §8
and spec psp_file_format §6.7 both put "a record runs past its block" under corrupt input. Nothing
pinned `decode_record`'s class at all: applying the fix as a mutation left all 53 tests green.

**B2: [record.rs:1133](../../../../src/ng/psp/record.rs#L1133) — a decoded head can put a record's end on the coordinate ceiling, and the region it hands out panics whoever asks its width**
**Categories:** reliability, and as a Major in errors, refactor_safety, idiomatic and extras — **five
in all.** **Confidence:** High.
Four bytes of untrusted input decode to a region ending at `u64::MAX`.
[`GenomeRegion::len()`](../../../../src/ng/types.rs) is documented as wrong at exactly that value —
it adds one to `end` before subtracting. Reproduced: `panicked at src/ng/types.rs:105:9: attempt to
add with overflow`, from a call the module's own C2 test already makes. In a release build the same
input reports a length of **0** for a region spanning a base. `RecordEncoder::push` has the mirror
hole through `record.region.len()`: it panics in a test build, and in release writes a
`reference-span` of 0 — a record its own reader refuses — and returns `Ok`.

### Major

**M1: [record.rs:1036](../../../../src/ng/psp/record.rs#L1036), [:1107](../../../../src/ng/psp/record.rs#L1107) — the offset base is a bare `Position` and every wrong one is silent**
**Categories:** refactor_safety, idiomatic, defaults — **three.** **Confidence:** High. Measured:

```
reader stale by one record:  got [90667287, 90667294, 90669993], truth [.., 90670000], consumed 206 of 206
writer stale by one record:  got [90667287, 90667294, 90670007]
writer handing each record its own start: got [90667287, 90667287, 90667287]
```

No `Err` in any of the three, and the stale-base walk consumes the run exactly, so it looks healthy.
The proptest hands encoder and decoder the *same* base, so it pins self-consistency and cannot see
this.

**M2: [record.rs:105](../../../../src/ng/psp/record.rs#L105) — C1's Blocker is only half closed: the declared *encodings* are pinned by nothing**
**Categories:** defaults, smells, extras — **three.** **Confidence:** High.
Declaring `record-body-byte-count` as a 4-byte fixed-width integer while the encoder writes a
varint passes all 97 tests, and so does the same mutation on C1's `mapq-sum`. The longhand test
asserts `field.name.0` only. The gap covers all 23 fields.

**M3: [record.rs:1074](../../../../src/ng/psp/record.rs#L1074) — the `RecordHead` the encoder hands back is asserted by nothing**
**Categories:** reliability, extras. **Confidence:** High. Three independent mutations of the
returned struct — its region, its body length, its non-reference count — each left `97 passed`.
Milestones D and F build the block index from that value rather than by re-reading the bytes.

**M4: [record.rs:1141](../../../../src/ng/psp/record.rs#L1141) — the head's two `u32` narrowing guards have no test — C1's fixed M3, reintroduced at new fields**
**Categories:** reliability, errors, idiomatic, extras — **four.** **Confidence:** High.
`read_varint(..) as u32` survives. Under it, a declared body length of 4,294,967,301 becomes 5: the
reader takes a five-byte body out of the middle of a record and calls the result a record.

**M5: [record.rs:1190](../../../../src/ng/psp/record.rs#L1190) — `bytes_in` is measured from the body for a body fault and from the record for a head fault, out of one call**
**Categories:** errors, naming, reliability. **Confidence:** High. Measured `76`, `81` and `10` on
a record with a four-byte head. The field exists because a field name alone does not say where to
look; a number whose origin depends on which half failed does not either.

**M6: [record.rs:1143](../../../../src/ng/psp/record.rs#L1143) — the head got one half of C1's error-classification pair and not the other**
**Categories:** reliability. **Confidence:** High. C1's fix put two tests on the body —
`Truncated`-at-every-cut and `Malformed`-for-a-length-no-body-could-hold — and the doc names them as
"the two tests that hold the line". C2 added only the first.

**M7: [record.rs:1067](../../../../src/ng/psp/record.rs#L1067) — `RecordEncodeError`'s three variants are not the complete set**
**Categories:** errors, refactor_safety, extras. The coordinate ceiling is a fourth thing the head
cannot describe. (Same defect as B2, filed on the write side.)

**M8: [record.rs:89](../../../../src/ng/psp/record.rs#L89), [:271](../../../../src/ng/psp/record.rs#L271), [:1060](../../../../src/ng/psp/record.rs#L1060) — "a body is at most `u32::MAX` bytes" is written in three places and pinned in none**
**Categories:** refactor_safety. **Confidence:** High. Widening the field to `u64` passes all 97
once an incidental `size_of` assertion is relaxed; loosening the ceiling to `u64::MAX / 2` passes
with nothing relaxed, because its guard tests are written in terms of the constant itself. **Both
survivors flip a fault from `Malformed` to `Truncated`.**

**M9: [record.rs:2616](../../../../src/ng/psp/record.rs#L2616) — the skip test compares a walk against itself, and C3's oracle is specified in the same shape**
**Categories:** reliability. **Confidence:** High. `decode_record` returns `read_record_head`'s head
and byte count verbatim, and both walks reach it with equal arguments, so "the same heads and the
same final byte" is arithmetic. Proven: with the two fixture-anchored assertions deleted and an
off-by-one applied to the span rebuild, **the test passes**. The anchors are the oracle; the
agreement between the walks is not.

**M10: [record.rs:1107](../../../../src/ng/psp/record.rs#L1107) — no arbitrary-input property test over the two new parser entry points**, though C1 built one for the body. The Blocker is precisely what such a test finds.
**Categories:** reliability.

**M11: [record.rs:1179](../../../../src/ng/psp/record.rs#L1179) — the head's `non_reference_reads` is never checked against the body**
**Categories:** extras. A head reading 0 over a body holding 19 non-reference reads decodes
cleanly — the shape that makes a varying position invisible to the cohort's first pass. The count
is derivable from the body just built.

**M12: [record.rs:110](../../../../src/ng/psp/record.rs#L110) — the wire name `body-bytes`**
**Categories:** naming. Three things at once: spec §4.3 spells the field `record_length` and the
departure is recorded nowhere; `body` alone is the word C1 paid to qualify, and the manifest *is*
the header's TOML body, whose own length `header.rs` calls `body_bytes`; and in a name-only field
list it reads as a byte string beside `reference-bases`, where the list spells its counts
`observation-count`.

**M13: [record.rs:82](../../../../src/ng/psp/record.rs#L82) — `non_reference_reads`'s doc says "summed over the observations"**, and only observations that spanned the whole locus are counted. The same doc says zero means "nothing varies here", which is what a filter author reads.
**Categories:** naming.

### Minor and Nits

Thirty-one between the eight, of which the ones acted on: the module diagram shows a
`chain_id_changes` head field no code writes and spells the others with underscores where the
manifest uses hyphens; `the_manifest_declares_the_head_before_the_body` is wholly contained in the
golden-names test; `positions_are_rebuilt_…`'s fixture has a first gap of 7 and a first span of 7,
so it never exercises the case its own doc claims; `three_records_in_order` is largely fixture noise
(zeroing eight of one record's numbers leaves the suite green); `HEAD_FIELDS` sits under the "The
body" banner and `HEAD_` already abbreviates *header* in this module; `BodyReader` reads heads now
and its doc, its binding and its messages all say "body"; `bytes_read` names two different
quantities in one expression; five spellings of the base position, two of them bare adjectives;
`RecordInBuffer` names a container, and "buffer" is a word spec §4.4 has already assigned;
`RecordEncoder::push` leaves `decode_record` with no visible twin; `BodyTooLong` has no test and no
reachable fixture; "nothing written before refusing" is real, stated nowhere, and asserted for one
of three refusals; two records at the same start are accepted with nothing saying whether that is
intended; three measurement-quoting slips — an unsourced "99 positions in 100", a duplicated 2.06×
sentence, and the decoder's 20 M records/s attached to the writer's path; and two test fixtures both
called `quiet`, one of them the module's richest record.

## 7. Out of scope observations

- **[src/ng/types.rs:104](../../../../src/ng/types.rs#L104)** — `GenomeRegion::len()` is documented
  as wrong at `end == u64::MAX` and left that way, with the hazard delegated to each caller.
  `psp::record` is the second caller to have to work around it, and it is the proximate cause of
  both halves of B2. A `checked_len()` would close it at the source. **For the `ng::types` owner.**
- **The head-only walk is now measured, and it is not the spec's number.** 30,000 records of 68
  uncompressed bytes, no compression: head-only **0.0006 s** against a full decode **0.0095 s**, so
  **16.7×**, and 13.5× keeping one record in a hundred. The spec's 2.06× includes 0.104 s of
  decompression on both sides and records of about 5 compressed bytes; stripping decompression out
  of the spec's own table gives a parse-only 5.3×, which is what the 13.5× should be read against.
  **The direction holds and H5 still owes the real number** on a real sample.
- **`PspWriteError` has no home for two of `RecordEncodeError`'s variants**, the write-side
  counterpart of C1's deferred M13. Recorded, for F3.

## 8. Missing tests to add now

All are in the fixes. In brief: the encoder's returned head against the bytes; the head's `u32`
guards; the coordinate ceiling on both sides; a fault inside a bounded body, with the same input run
again over a grown buffer; a whole record cut at every byte through `decode_record`; a head
under-declaring its body; the `non_reference_reads` disagreement; the body-byte ceiling written
once; a head declaring a 4 GiB body; a base stale by one record; a record at 300 reads a position,
where the head's fields stop fitting in one byte; and an arbitrary-bytes property over both entry
points that asks the decoded region for its width.

## 9. What's good

- **Every half-applied Milestone E change fails loudly.** A chain-id field added to the head's
  encoder only, after the body only, or to the decoder only each failed 7 tests; added to both sides
  with the manifest left alone, it still failed 2. `RecordHead` needs no change, exactly as its doc
  claims.
- **A head field written in the wrong order is caught twice over** — by the golden four bytes, whose
  values are pairwise distinct so no permutation survives, and by the manifest test that swaps every
  adjacent pair of the 23.
- **A field inserted at the seam between the head's fields and the body's is caught on both sides**,
  by the golden name list and by the seam assertion.
- **Adding a field to `RecordHead` is a compile error at four sites** — both production literals
  name every field.
- **The parse is sound against hostile input**: 811,520 fuzzed inputs against eight base values
  including `u64::MAX`, overflow checks live, no panic and no `Ok` over-reading.
