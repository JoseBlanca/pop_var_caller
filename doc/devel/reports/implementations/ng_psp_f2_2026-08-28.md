# ng psp store — F2: the footer, magic last

*Implementation report, 2026-08-28. Step F2 of
[`../../ng/impl_plan/psp_file_format.md`](../../ng/impl_plan/psp_file_format.md), branch
`ng-psp-encoding`. Design authority: [arch §3.4](../../ng/arch/psp_file_format.md),
[spec §3.3](../../ng/spec/psp_file_format.md).*

---

## 1. What the step is

**The fixed 48-byte tail whose presence is what says a file is finished.** `Footer` existed as a
type from A1; this is its codec and its refusals.

It carries where the index and the trailer are and how long each is, how many blocks the file
holds, a checksum over the index, and the magic — **last**, so a four-byte read at end-of-file
rejects a foreign or unfinished file before anything else is touched.

**This is the step goal 3 rests on.** A psp with no valid footer is a run that was killed
part-way, and there is no safe way to read one short: the caller would get a sample that stops in
the middle of a chromosome and says nothing about it. H2 tests that end to end; F2 is what makes
the refusal possible, and F4 is what raises it.

## 2. Decisions taken here

### 2.1 What a footer can check about itself, and what it cannot

Production's decoder checks the magic and nothing else, saying self-consistency across the file
is "the reader's responsibility". ng checks three things, and they are exactly the three that
need no knowledge outside the 48 bytes:

- **the magic**, before any offset is believed;
- **neither section's offset-plus-length overflows** — refused rather than wrapped, because a
  wrapped sum is a small number that looks like a legal offset;
- **the index ends exactly where the trailer begins.** They abut by construction (spec §3), and
  it is what makes replacing a trailer a truncate-and-write-forward (spec §6.5): a gap would
  leave stale bytes inside the file, an overlap would eat the end of the index.

**What it deliberately does not check** is written on the function: nothing here knows the file's
length, so nothing here can say the trailer ends where the footer begins or that the index lies
inside the file at all — that is `open`'s, which has the length. And the block count is not
checked against the index's byte length, because `decode_index` already requires the bytes to
hold exactly that many entries and no more, which is the exact form of the same check.

### 2.2 The magic is checked first, and a test says so

Not merely *present* but *first*: a footer whose numbers are nonsense **and** whose magic is
wrong must be refused for the magic, because that is the answer a caller can act on — *this file
was never finished, rebuild it* — where the arithmetic would only say it is damaged. Moving the
check after the offsets is caught by three tests.

### 2.3 Two error classes, because two instructions

`FooterDecodeError::NotAFooter` means *the writer never finished, or this is not an ng psp*. The
other two mean *this file is damaged*. F4 maps them apart: the first is `Incomplete`, which is
the everyday case of a killed pileup, and the rest are corruption. Keeping them one variant would
lose exactly the distinction goal 3 is about.

Like this module's other codec errors, the type carries **no path**; the file's name belongs to
whoever opened it.

### 2.4 The encoder destructures

`encode_footer` takes the fields apart with no `..`, so a field added to `Footer` is a compile
error there rather than a field silently left out of every file this build writes. That guard
comes straight from F1's review, where an encoder reading fields one at a time dropped a new
field with the suite still green — and it matters more here, because the footer's width is also
a seek distance.

| test | what it pins |
|---|---|
| `a_footer_round_trips_field_for_field` | three shapes, including a file with no blocks and an empty trailer |

| `the_magic_is_the_last_four_bytes` | the property the end-of-file read depends on |

## 6. Trade-offs and follow-ups

- **`no_byte_of_the_footer_is_ignored` is the closest thing here to a completeness proof**, and
  it is weaker than it looks: it says every byte is *read*, not that every byte is *checked*.
  A footer field nothing validates still round-trips to a different value, which is enough to
  catch a byte a writer left uninitialised — spec §7's worker-count invariance — but not enough
  to catch a field whose value is never sanity-checked. Those checks are `open`'s.
- **The width is 48 bytes and that is now asserted three ways**: the field-sum test from A1, the
  golden-bytes literal, and `FOOTER_BYTES` itself. From Milestone F a change to it costs a format
  version.
