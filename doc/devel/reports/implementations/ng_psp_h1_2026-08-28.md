# ng psp store — H1: parity with the measuring prototype

*Implementation report, 2026-08-28. Step H1 of
[`../../ng/impl_plan/psp_file_format.md`](../../ng/impl_plan/psp_file_format.md), branch
`ng-psp-encoding`. Design authority: [arch §8](../../ng/arch/psp_file_format.md),
[arch §2](../../ng/arch/psp_file_format.md).*

---

## 1. What the step is

**Does `src/ng/psp/` give back the records it was handed, and does an encoder that is not it
agree?**

Every figure and every claim of fidelity the psp specs carry was taken on the measuring prototype
(`examples/psp_row_stream_roundtrip.rs`) over production's `PileupRecord`. This step is the first
time the module that shipped is checked instead — over a real corpus rather than a forty-record
fixture, and against a codec written before it and sharing no code with it.

`examples/ng_psp_parity.rs` takes one production `.psp`, turns every record in it into an ng
record, writes **both** stores from that same sequence, and walks all three streams in lockstep.

## 2. Decisions taken here

### 2.1 Three streams, because a round-trip through one codec proves only self-consistency

| pair | what a disagreement means |
|---|---|
| the ng record pushed → the ng record read back | `src/ng/psp/` lost or changed a field |
| the ng record read back → the prototype's record read back | the two encoders disagree |
| the prototype's record → the source record | the prototype moved a number |

**The second pair is why this step is not just a round-trip test.** An encoder that writes a field
wrongly and a decoder that reads it back the same wrong way agree with each other perfectly.

**Measured, not argued:** a defect planted in the harness's *own* mapping — reading `mapq_sum` as
`mapq_sum + 1` out of the source — leaves the round-trip pair passing, because both sides carry
it, and fails at `record 0, allele 0: mapq_sum, against the prototype`. That is the second arm
earning its place.

### 2.2 The prototype is included whole, and only its visibility changed

An example cannot depend on another example, and copying its encoder in would have made the oracle
a fork of itself. `#[path = "psp_row_stream_roundtrip.rs"] mod prototype;` keeps one copy. **Seven
declarations became `pub(crate)`** — `Scales` and its three fields, `encode_streaming`,
`StreamingStore`, and its `open` and `next`; **no line of its behaviour was touched.**

Including it puts the prototype in the clippy gate for the first time — `--lib --tests` reaches it
because the parity example is `test = true` — and it has two findings there, an unread assignment
and a ten-argument function. **They are allowed at the `mod` declaration rather than fixed**: an
oracle edited to please a lint in the code it is checking is a little less of an oracle.

### 2.3 The prototype is asked for ng's own step, so the summed log-error is compared *exactly*

The prototype stores that field as an integer count of steps at a scale written into its file. Its
default is 1/256 of a natural log; ng's is 1/4,096 since Milestone B3. Asking the prototype for
4,096 makes both stores round the same `f64` to the same integer, so the cross-arm comparison is
**equality**, not a tolerance wide enough to hold both — which is the shape the plan warns about
when it says a blanket tolerance would pass while a chain-id list was being corrupted.

The step still appears once, in the right place: **against the source `f64`**, where each store is
required to be within half a step. Measured, worst case over both corpora: **0.000122064 against
a half-step of 0.000122070** on hg002, 0.000122030 on tomato.

### 2.4 Chain-id lists are compared as sets, and the harness reports whether that mattered

ng's encoder writes a list as ascending gaps, so a list arrives back sorted and deduplicated
whatever order it went in — the encoder says so, and `SequenceObservation::chain_ids` is defined
by what the ids mean rather than by their order. The harness normalises the pushed list the same
way and **counts the lists the normalising changed**.

On both corpora that count is **0**: production's lists are already sorted sets, so the comparison
was in fact exact everywhere it ran. The line is in the report so a reader can see that rather
than take the concession on trust.

### 2.5 ⚠ The corpus synthesises the four fields production has no equivalent of

Arch §2 lists what ng's record carries that production's does not: the read witness, the read
group, and the two counts of reads that showed nothing. Left at their empty values — `Complete`,
group 0, zero, zero — **a corpus cannot tell an encoder that stores those fields from one that
drops them.** All four are derived from each record's own coordinate, so the corpus is still a
function of its input and two runs give the same file.

**This is not hypothetical. It was found by a mutation that survived.** With both counts at zero,
an encoder writing a constant `0` for `reads_discarded_by_cap` passed a 3,000-record parity run
over hg002 — the only one of six injected defects that did. With the counts synthesised it fails
at record 0. `assert_the_corpus_can_fail` now holds every one of these shapes as a precondition,
asserted before any parity claim is made.

The witness is minted in three shapes on purpose, because each is a different thing to get wrong:
`Complete`, which is a run count of zero on the wire; a `Partial` covering the whole locus, which
must **not** come back as `Complete`; and a `Partial` with a hole in it, which is what a spliced
read across a widened record looks like and what a two-number witness could not express.

## 4. What the two corpora say

Both runs compared every field of every record and every observation, and both passed.

| | hg002 chr21 | tomato SRR7279481 |
|---|---:|---:|
| records compared | 74,623 | 7,687,686 |
| observations | 123,263 | 8,049,472 |
| blocks the ng store cut | 598 | 879 |
| chain ids compared | 150,720 | 555,022 |
| chain-id lists the normalising changed | 0 | 0 |
| records naming at least one read | 34,482 | 348,146 |
| records with more than one observation | 34,482 | 348,146 |
| witnesses: complete / partial / with a hole | 41,115 / 82,148 / 691 | 2,682,951 / 5,366,521 / 442 |
| records with reads that showed nothing | 63,981 | 6,589,480 |
| records with reads the cap discarded | 49,730 | 5,125,099 |
| worst summed-log-error against the source | 0.000122064 | 0.000122030 |

*Half a step is 0.000122070.*

**Witnesses with a hole are rare because production's records are one position long.** A hole
needs three positions, and a production record's span is its reference allele's length, which is 1
except at an indel — so 691 of 123,263 on hg002. The count is asserted non-zero rather than left
to chance, and the unit tests hold the shape directly.

**The two counts above coincide** — 34,482 and 34,482, 348,146 and 348,146 — although they are
tallied independently, one per record naming any read and one per record with more than one
observation. Whether every such record is the *same* record was not checked, and no claim here
rests on it.

## 5. Tests added

**Twenty-three, in the example, run by a plain `cargo test`.** What they hold is that the
comparison **can fail** — the one thing a parity harness cannot demonstrate by passing, since a
comparison that had quietly stopped looking at a field would report the same clean run over eight
million records.

Nine change one field of an agreeing record and require the refusal: the witness collapsed to
`Complete`, the witness with its hole closed, the read group zeroed, a chain id dropped, the
summed log-error one step out, a lost count of reads that showed nothing, and — on the prototype
pair — the summed log-error, an allele sequence and a chain-id list.

Seven hold the preconditions, one per shape `assert_the_corpus_can_fail` refuses: a single-block
corpus, a corpus naming no reads, one of single-observation records, one whose witnesses are all
`Complete`, one with no hole in any witness, one of a single read group, and one where the cap
discarded nothing.

The remaining seven are the baselines and the two concessions: that an unchanged record is
accepted on *both* pairs and that a corpus meeting every precondition is accepted — without those
two, every `should_panic` above could be passing for the wrong reason — that a list which came back
sorted is accepted **and counted**, that a `Partial` covering the whole locus stays `Partial`, that
a hole needs three positions, and the md5 and basename parsing the header demands.

**Seven defects injected into `src/ng/psp/record.rs`, seven caught** — and *where* they were caught
is worth recording, because it is not all one place:

| defect | caught by |
|---|---|
| the read group is written as 0 | the comparison |
| the summed log-error is written one step out | the comparison |
| the reference bases lose their last byte | the comparison |
| `reads_without_observation` is written as 0 | the comparison |
| `reads_discarded_by_cap` is written as 0 | the comparison |
| every witness is written as `Complete` | **the reader's own guard** |
| a chain id is dropped from a stored list | **the reader's own guard** |

**The last two never reach the comparison**, and the mechanism is worth knowing. The head's
`non_reference_reads` counts only observations whose witness is `Complete`
([`locus_generation/mod.rs:263`](../../../../src/ng/locus_generation/mod.rs)), so rewriting the
witness changes the count the reader recomputes from the body and the head/body agreement check
refuses the record — *`a head reading 0 over a body whose reads show 1`*. Dropping a chain id
breaks the residual derivation the same way: *`a derived list of 2 reads where the record says
1`*. Both are real catches; neither is evidence that the comparison holds those fields, which is
what the unit tests are for.

## 7. Trade-offs and follow-ups

- **The corpus is production's records, not ng's.** ng cannot yet write a psp of its own — that is
  [`run_streaming.md`](../../ng/spec/run_streaming.md)'s — so four fields are synthesised and the
  record shape is production's: spans of 1 except at indels, and no `LocusKind::Ssr`. **The
  locus kind is therefore `Generic` on every record in both corpora**, and no parity run has yet
  exercised the SSR arm of the kind codec. The unit tests do not reach it either. It is held by
  `record.rs`'s own tests and by nothing here.
- **The harness runs on files under `tmp/`, which are not in the repository.** The suite gets the
  23 unit tests; the eight-million-record run is a command someone types. The two corpora used are
  `tmp/d2/hg002_chr21.psp` and `tmp/d2/tomato_SRR7279481.psp`.
- **The grid is 10 kb here, not the settled 100 kb.** Measured both ways: at 10 kb the two corpora
  cut 598 and 879 blocks, at 100 kb they cut 281 and 160 — so the shipped grid gives tomato a
  *fifth* of the block boundaries. Every running difference in the format resets at a boundary, so
  the smaller grid is the stricter test; what it costs is that no parity run has been taken at the
  size the format actually ships with. Both grids pass — the 100 kb runs above were full parity
  runs, not block counts taken on the side.
- **The prototype re-encodes the whole file even under `--limit`.** `encode_streaming` takes no
  limit, so a limited run still pays the prototype's full pass over the source. Not worth changing
  the oracle for.
