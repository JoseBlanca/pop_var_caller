# ng psp store — G1: a coordinate to a block, and the walk that follows it

*Implementation report, 2026-08-28. Step G1 of
[`../../ng/impl_plan/psp_file_format.md`](../../ng/impl_plan/psp_file_format.md), branch
`ng-psp-encoding`. Design authority: [spec §6.2, §1.2, §3.3](../../ng/spec/psp_file_format.md),
[arch §4.1](../../ng/arch/psp_file_format.md).*

---

## 1. What the step is

**Three ways to start reading a psp's records, and the walk they all hand back.**

```rust
psp.records()?                      // from the first block
psp.records_from_block(n)?          // from block n, by ordinal into `block_index()`
psp.records_from(at)?               // from the block holding a coordinate
```

Each returns a `RecordIter` — a lazy iterator over `Result<StreamedRecord, PspReadError>` that
borrows the reader, holds nothing that grows with the file, and yields `Err` once and then
`None`.

Milestone D built the streaming reader and Milestone F opened the file. What was missing between
them was the two things this step adds: **turning a coordinate into a byte offset**, and
**telling the walk where the blocks stop**.

## 2. The design question the step was handed, and how the documents answer it

**Asked:** a record can span past the next block's first position, and ng's index cannot see it —
production's index entry carries a `last_pos` its overlap predicate needs and ng's dropped it
deliberately (spec §3.3). So when `records_from(contig, position)` picks the block whose first
position brackets the coordinate, a record in the *previous* block may still cover that position:
a deletion widens a record past its own block.

**The documents settle it, and in the same direction twice.**

- Spec §6.2: "the position asked for is where the **records start**, not where the reading
  starts" — the coordinate is matched against where records begin, not against what they span.
- Arch §4.1, on `records_from`: "**Reading starts at that block's first record**, not at
  `position` — a reader cannot start mid-block."

So `records_from` is a **block-selection convenience, not an overlap query**, and the walk it
returns begins at the chosen block's first record — which is at or *before* the coordinate asked
for, usually well before it, since a block spans 100 kb by default. Two consequences, both
written into the doc comment and both tested:

- a caller wanting only records from `at` onwards drops the ones in front itself, at the cost of
  a head each and no body;
- a caller wanting the records *covering* a coordinate starts a block earlier and reads their
  spans. **The container cannot offer more**: an index entry carries a block's first position and
  nothing else, and §3.3 removed the only field that could have said how far a block's records
  reach.

`a_record_spanning_into_the_next_block_is_not_in_a_walk_that_starts_there` pins both halves —
that the file really holds a record starting at 900 and covering 1,100, and that asking for 1,100
does not return it.

**One wording note for the owner, not a blocker.** Spec §6.2's sentence also admits a reading
under which `records_from` would *skip* to the coordinate asked for, discarding the earlier
records of the block. Arch §4.1 is unambiguous against that, and the code follows the arch. If the
spec's sentence is meant the other way, this is the line to change and G1 is the code that would
change with it.

## 3. Decisions taken here

### 3.1 The walk is a file of its own, because `open` must stay unable to reach a block

F4's review added `the_opener_cannot_reach_any_block_decoding_code`, which reads `reader.rs`'s own
imports and asserts it names neither the block module nor the record module — a structural
statement that opening cannot inflate anything, which is stronger than the behavioural test beside
it.

**Building the walk inside `reader.rs` would have added exactly the import that test forbids.**
So `walk.rs` takes the file already seeked and already bounded, and `reader.rs` contributes the
index lookup, the seek and the bound. The property survives the feature that would have ended it,
and the guard test now says why.

### 3.2 The source is bounded at the index, which is what stops a walk reading the file's tail

A `BlockStream` reads blocks until its source runs out, and **a psp does not end with its
blocks** — the index, the trailer and the footer follow. Handed the whole file it would take the
index's first four bytes for a block length and try to inflate what came after.

So the walk gets `file.take(index_offset − block_offset)`, and the blocks' end arrives as an end
of file, which is the one thing a stream already stops cleanly on. It also gives the empty psp
for free: no blocks means the walk starts at the index offset and is bounded at zero bytes.

**Measured rather than argued.** With the bound replaced by `u64::MAX` on the eight-block fixture,
the walk reaches a ninth block that does not exist and zstd refuses it:

```
CorruptBlock { block: 8, source: Zstd { while_doing: "decompressing a block",
               said: "Unknown frame descriptor" } }
```

### 3.3 A block-read failure is put in the class whose instruction fits it

`BlockReadError` already separates *the file is damaged* from *upgrade the reader* from *raise a
limit*; `CorruptBlock`'s own doc comment (written at C1, restated at D1) warns against flattening
them, because *rebuild the file* is wrong advice for two of the three. So the walk maps them to
three read-error classes rather than one, and spec §7's table is the list:

| what the block reader said | what the caller gets | the instruction |
|---|---|---|
| a frame that will not inflate, a record past its block, a block holding more than it declared | `CorruptBlock` | rebuild the file |
| a record needing more of the buffer than one record may hold | `RecordLargerThanTheReaderAllows` | raise the ceiling |
| a record, or a manifest field, this build does not read | `UnsupportedRecordEncoding` | upgrade the reader |
| the file's bytes could not be read | `Io` | the usual |

### 3.4 A block is named by its ordinal, and the count comes from the stream

`CorruptBlock { block }` is the ordinal into `block_index()`, so a caller can look the block up.
Nothing the walk already held could produce it: a block whose head never parsed has no
`BlockHead`, and **two blocks may legitimately share a first position** (`index.rs`), so counting
distinct coordinates would not separate them. `BlockStream` therefore gained
`blocks_begun()` — incremented the moment a block's declared length has been read, so a fault
inside a block's head is a fault *of that block*.

The one case that needs care is a fault in the four bytes that *introduce* a block, which are read
before it is counted: `refuse` names that one as one past the last block that began.

### 3.5 An ordinal the file does not have is an error, not a panic

`records_from_block(n)` with `n` past the end is `PspReadError::NoSuchBlock`, naming both numbers.
It is the one variant of that enum that reports a caller's mistake rather than the file's — the
enum's doc now says so — and it is an error rather than the panic a slice index would give
because the caller is a cohort holding thousands of psps open: an ordinal computed wrongly must
fail one sample, not abort the run. `records_from` cannot raise it, deriving its ordinal from the
index itself.

### 3.6 Carried forward from F, and landed here

- **`PspReadError::Damaged` carries its cause.** Four different causes reached it as one string;
  the footer decoder's and the block index decoder's own errors are now kept as `#[source]`, and
  the rules `open` checks itself — the ones needing the file's length, which no codec has — carry
  `None`. Two constructors (`damaged`, `damaged_by`) keep the call sites readable. *The write-side
  `reason: String` variants are G3's, where the writer's surface is the one being extended.*
- **`blocks()` is now `block_index()`**, which is what every document about this format calls that
  section (spec §3.3) — and a caller reading `psp.blocks()` beside `psp.records()` reasonably
  expects the blocks themselves.
- **`head_magic` is now `read_the_head_magic`**, a verb for a function that seeks, reads and
  leaves the cursor at byte 4; its unused `path` parameter is gone.

## 5. Tests added

**Thirteen**, all in `walk.rs`. The four that carry the most:

**`a_walk_from_any_block_is_the_tail_of_a_walk_from_the_first`** — restart equals sequential,
through the file's own surface rather than a buffer. For each of the fixture's 8 blocks, the walk
from that block is compared against the tail of a full walk. **The block each record belongs to is
taken from the walk's own `blocks_read()`, not from comparing coordinates**, because two blocks
may share a first position and a coordinate therefore does not identify one.

**`a_walk_ends_at_the_last_block_and_never_reads_the_index`** — the walk ends with `None` and not
`Err`, having opened exactly the 8 blocks the index names. Without the bound of §3.2 it reaches
the index and refuses.

**`a_record_spanning_into_the_next_block_is_not_in_a_walk_that_starts_there`** — §2's design
answer, both halves asserted.

**`a_record_larger_than_the_reader_allows_is_refused_by_name`** — a genuine 400,000-base record,
written by this writer and refused by name with the 512 kB ceiling in the message rather than
reported as a corrupt block. It is the one class spec §7 splits out because *raise the ceiling*
and *rebuild the file* are opposite instructions.

The rest: every record written comes back in order and equal, against `a_sample` rather than
against the walk itself; `records_from` on every block's own first position starts that block; a
coordinate 50 bases into a block starts that block's *first* record, and one in front of every
block starts the first; a psp with no records walks to nothing from both entry points; an ordinal
past the last block is refused naming both numbers while the last block still walks; a block
filled with `0xff` is named as block 2 and ends the walk after the 10 records of the two blocks
before it; a manifest naming a field this build does not read there is *upgrade the reader* and
not damage; and `Damaged` carries the index decoder's own error where there is one and `None`
where `open` measured the file itself.

**Twelve defects injected, twelve caught**, every mutation asserting its anchor matched exactly
once before running:

| defect | caught by |
|---|---|
| the source is not bounded at the index | 6 |
| `records_from` lands one block late | 3 |
| the block search is strict where it must be inclusive | 1 |
| `records` never finds the first block | 6 |
| the failing block is named one late | 2 |
| blocks are never counted | 3 |
| every error cause is dropped at the helper | 1 |
| a bad ordinal is clamped instead of refused | 1 |
| the seek is dropped | 4 |
| a too-large record is reported as damage | 1 |
| another build's manifest is reported as damage | 1 |
| an empty psp is refused a walk | 1 |

## 7. Trade-offs and follow-ups

- **The record-buffer ceiling is not a knob on `PspReader`.** `RecordLargerThanTheReaderAllows`
  says *raise the ceiling*, and today the ceiling can only be raised on a `BlockStream` directly —
  a `PspReader`'s walk always uses the 512 kB default. The message states the number without
  promising a setter. Giving the reader one means either a third `open_*` constructor or a second
  caller-mistake error variant, and neither is worth doing before a caller needs it.
- **F4 left one follow-up addressed to this step**: spec §4.2 calls a frame needing a wider window
  than the header declares "a corruption worth detecting rather than tolerating", and F4 noted
  nothing detected it. **It is detected, by construction**: `BlockStream::new` configures zstd's
  `WindowLogMax` from the manifest and zstd refuses a wider frame, which arrives here as
  `CorruptBlock`. That zstd does refuse it is block.rs's
  `the_shipped_settings_cap_a_payload_larger_than_the_window`; **no test drives it through a
  file**, because building one means assembling a psp whose blocks were compressed outside this
  writer.
- **`records_where` is G2**, and it is where `RecordIter` gains a predicate. The natural shape is
  for the two to share one type, with `records()` the predicate-free case.
- **A walk borrows the reader**, so a psp has one walk at a time. That is arch §4.1's contract and
  it costs no second file handle per sample — but a caller wanting two positions of one file at
  once opens it twice.
