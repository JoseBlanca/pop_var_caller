# ng psp store — E2: a read goes live, stops, and goes live again

*Implementation report, 2026-08-27. Step E2 of
[`../../ng/impl_plan/psp_file_format.md`](../../ng/impl_plan/psp_file_format.md), branch
`ng-psp-encoding`. Design authority:
[`../../ng/spec/psp_record_encoding.md`](../../ng/spec/psp_record_encoding.md) §6 and
[`../../ng/spec/psp_chain_id_encoding.md`](../../ng/spec/psp_chain_id_encoding.md) §5.*

---

## 1. What the step is, and why it is its own commit

**A chain id names a read *pair*, with the mates collapsed onto one identifier — and a pair's mates
rarely overlap.** So the identifier covers two stretches of reference with an unsequenced hole
between them: it goes live, stops, and goes live again.

Spec `psp_record_encoding.md` §6 measures how often, on real alignments: **83 % of identifiers on
the human sample and 91 % on tomato**. And it says what a differential stream that assumed one
stretch per identifier would do — *"loses the second mate of nine reads in ten — silently, because
the merge would simply see a read that was not there."*

That is why the plan gives this its own commit with its own oracle. **The failure has no symptom.**
A file written by a one-stretch-per-id writer parses perfectly; every record's set is a plausible
set; and the cohort merge, which asks only *was this read here*, answers *no* for a read that was
there — the exact question the whole chain-id column exists to answer.

## 2. ⚠ E1's encoding already handles it, and this step adds no bytes

Arrivals and departures express re-entry with no notion of *how many times*: an identifier that
departed at one record and arrives at a later one is an ordinary arrival, because nothing in the
codec remembers what has been named. So — as at C3, D4 and D5 — this step could not find a bug,
because there was none to find.

**What it owes is the oracle**, and the plan names it: *counts two-stretch ids on the fixture and
asserts they all come back*.

**One thing E1 owed and did not have**, found by its review and fixed there: no fixture ever made an
arriving identifier sort below one already live, so both interleaving arms of the module's two
merges were dead code under test. A returning read is exactly that shape. E1's fix made the arms
reachable with a hand-built five-record fixture; this step makes them reachable with coverage that
looks like reads.

## 3. What the tests are

Four new — `ng::psp::chain_ids` from 23 to 27, `ng::psp` from 224 to 228.

| test | what it forces |
|---|---|
| `most_reads_go_live_twice_and_every_one_of_them_comes_back` | **the plan's oracle** — §4 |
| `a_read_that_comes_back_across_a_block_boundary_arrives_again` | the two rules meeting: a read still covering at a block boundary is *restated*, not remembered, and a read whose second mate begins after the boundary arrives there with nothing saying it is the same read. **⚠ Its fixture had no read live across the boundary when this was written** — the restatement half of the claim was not exercised, and making the writer's `start_block` a no-op left the test green. [The review](../reviews/ng_psp_e2_2026-08-27.md) measured it; there is such a read now, and the mutation fails the test |
| `an_identifier_that_goes_live_five_times_reads_back` | *twice* being baked in anywhere. Two mates is what a pair gives, but a spliced alignment can leave more than one hole. *⚠ This row also offered "a read straddling two walked regions is named twice", which argues the other way: under an allocator that never reuses an id, being named twice gives **two identifiers of one stretch each**.* |
| `any_pattern_of_comings_and_goings_round_trips` | re-entry shapes a pair does not make, generated — three stretches, four, a read live only at the last record, one never live at all. **⚠ Its arrival count is self-consistent** — both sides come from the same records — so a draw with no re-entry satisfied it exactly, which its docstring denied; a `prop_assume!` throws those draws away now |

Plus a fixture generator and the oracle's own measure: `a_paired_end_coverage` builds pairs with a
hole between the mates, and `stretches_of` counts how many separate stretches each identifier
covers.

*⚠ The generator took four bare `u64`s, and the fixture could not tell two of them apart: measured
by the review, transposing the mate length and the gap between the mates gives the same 800
identifiers, the same 660 covering two stretches and the same 1,460 stretches, because a mate
starts at the sum of the two either way. They are named at the call site now, and one assertion
measures the mate length rather than only stating it.*

## 4. The oracle, and why it is not "the walk came out right"

**A walk over a paired-end fixture comes out right under a writer that loses every second mate**,
if all you compare is what the reader reconstructs from what the writer wrote. The two agree with
each other. So the test asserts three things, and the first two are about the fixture and the bytes
rather than about the walk:

1. **The fixture contains the thing, counted.** Measured: **660 of 800 identifiers cover two
   stretches — 82.5 %**, against the 83 % and 91 % the corpora give. A fixture that quietly stopped
   containing re-entry fails here rather than passing quietly.
2. **The writer emitted one arrival per *stretch*, not one per identifier.** 800 identifiers cover
   **1,460 stretches** over 400 records, so a stream that named each identifier once would carry
   800 arrivals and **lose 660 second mates**. The count is read off what the reader actually met,
   not inferred.
3. **And every record's set reads back**, so a second stretch that was written is also read.

The 140 identifiers that cover one stretch are the pairs whose second mate falls off the end of the
fixture — which is why the assertion asks for more than four fifths rather than for all of them.

## 5. Falsification — four defects injected

| defect injected | tests failed of 27 |
|---|---|
| **the writer names each read once a block, not once a stretch** — spec §6's named failure | 4 |
| the reader ignores a read it has already seen this block | 5 |
| a departure is never emitted, so a read never stops covering | 11 |
| **the stretch counter counts identifiers rather than stretches** — the oracle's own measure | 3 |

The last is the one worth having: an oracle whose measuring instrument is broken passes for the
same reason the code it is measuring would.

## 7. What E3 and E4 inherit

- **E3 puts these bytes in the record head**, and the silent failure there is the wiring: a writer
  that forgets `start_block` at a block boundary produces a file that parses perfectly and is wrong
  from that block's first record, because the reader restarts whether the writer did or not.
- **E4's residual is the live set minus the other observations' ids**, and re-entry is what makes
  the subtraction non-obvious: a read that is live at a record because its *second* mate covers it
  is in the set exactly once, whichever mate put it there. The count check spec
  `psp_chain_id_encoding.md` §5 names — *at most an observation's read count and at least half of
  it, since at most two mates share an id* — is the guard, and `stretches_of` is the fixture-side
  measure it can be checked against.
