## 1. What the step is

**The first code in this module that touches a file.** `PspWriter::create` writes a header,
`push` lays records down and writes each block as the cut rule closes it, and `finish` writes the
last block, the index, the trailer and the footer, and makes the file durable.

**Finishing is what makes the file readable at all.** Before it there is no footer, and every
reader refuses a file without one — the intended end for a run that was killed, and goal 3 of the
format.

## 2. Decisions taken here

### 2.1 `finish` reads back what it is about to write

**A writer must not be able to produce a file its own reader refuses.** F1 and F2 both raised
that obligation and both routed it here rather than solving it in their codecs, because each
module's own tests must be able to *write* the bytes that prove the reader refuses them.

`finish` is the one place where the bytes being written are meant to be readable, so the guard
belongs here: it decodes the index with `decode_index` and the footer with `decode_footer` —
**the very functions a reader will use** — and raises `WouldNotBeReadable` rather than leaving a
rejected file on disk. It costs one index decode and one 48-byte footer decode per file, against
a walk that wrote every block in it.

### 2.2 Nothing touches the filesystem until the header is accepted

`create` encodes the header and builds the cut rule and the compressor from its manifest
**before** `File::create`. A header this writer cannot honour therefore leaves no file at all,
rather than an empty one that every reader then refuses for a different reason. That is the
"state advanced before a failure can still be returned" lesson from Milestones D and E, applied
to the filesystem.

### 2.3 An index entry comes from the block's own bytes

The entry's coordinate is read back out of the block payload with `BlockHead::decode` rather
than kept in a number beside it, so **the index describes the file rather than the writer's
intentions**. Its offset is taken before the block is written and recorded only after.

### 2.4 ~~An I/O failure during `push` is terminal, and that is correct~~ — **this was wrong**

> The block being written is half on disk and the writer will not be finished, so the file keeps
> no footer and every reader refuses it. Nothing tries to unwind.

**That holds only while the failure persists.** A transient one — a device that fills and empties,
one refused write — left `finish` free to write a footer over a file with records missing from
the middle of a contig, which every reader accepts. The review measured it: `finish` returned
`Ok`, and contig 0 jumped from position 1,001 to 3,001. The writer now records that it lost a
block and `finish` refuses. See [the fixes](../reviews/fixes_applied_ng_psp_f3_2026-08-28.md).

### 2.5 The durability step is `into_inner`, not `flush` then `into_inner`

Spec §6.3 asks for three steps: flush the format, surface the buffered writer's errors, sync.
The first draft wrote `flush()?` and then `into_inner()?`, which *reads* like those three —
**and the middle one was unreachable.** A successful `flush()` empties the buffer, so the flush
inside `into_inner` has nothing left to write and cannot fail; deleting its error arm changed no
behaviour under mutation, which is how it was found. `into_inner` **is** the flush that surfaces,
so it is now the one call, and each of the three steps does work.

### 2.6 The block builder is held in an `Option`

`BlockBuilder::finish` consumes the builder — its own guard, since a builder closed twice would
put the last block in the file twice. So the field is takeable. It is `Some` for the whole of the
writer's life, because the only thing that takes it is `PspWriter::finish`, which consumes the
writer in the same breath.

Twelve, all writing and reading a real file in a temporary directory:

| test | what it pins |
|---|---|
| `a_finished_file_is_laid_out_the_way_its_footer_says` | the footer's offsets are checked against the file's own bytes: the index decodes there, its checksum matches, the trailer is the payload handed to `finish`, and the footer starts exactly where the trailer ends |
| `every_index_entry_points_at_the_block_it_names` | every offset in the index starts a whole compressed block, and lands in the blocks rather than in the index |
| `a_record_that_goes_backwards_is_refused_and_costs_the_file_nothing` | the refusal names the file, and the records after it still write |
| `a_contig_that_comes_back_is_refused` | a contig revisited gives a seek two runs to choose between |
| `a_header_that_cannot_be_written_leaves_no_file` | §2.2 — the path does not exist afterwards |
| `a_writer_dropped_without_finishing_leaves_a_file_with_no_footer` | **goal 3**: the file holds a header and blocks, does not end with the footer magic, and its header still reads |
| `a_sample_with_no_records_still_finishes` | an empty psp is a psp: no blocks, an empty index, a trailer |
| `an_empty_trailer_is_legal` | and the footer says so |
| `the_same_records_written_twice_give_the_same_bytes` | what spec §7's worker-count invariance rests on |

## 6. Trade-offs and follow-ups

- ~~**⚠ Nothing tests that a failed flush is surfaced.**~~ **Closed by the review**, which found the route: `/dev/full` accepts an open and fails every write, and the fixture is small enough that nothing reaches the device until `finish` flushes. The claim below was wrong.
  <br>~~Original:~~ No test here can make a real file's flush fail, and the durability contract is the
  one spec §6.3 flags as easy to get wrong. **H2 is where this is testable** — it kills a writer
  for real — and it is recorded there rather than papered over. The three earlier mutations that
  survived in this step were all my own no-ops; this one is not.
- **`append` and `replace_trailer` are not here.** They are G3 and G4, and both need `open`.
- **The readable-check does not verify the blocks**, only the index and the footer. Reading every
  block back would double the cost of a walk; the block codec's own round-trip tests are what
  cover it, and H1's parity oracle is what proves it end to end.
