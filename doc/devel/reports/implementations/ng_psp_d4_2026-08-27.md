# ng psp store — D4: the restartable parse

*Implementation report, 2026-08-27. Step D4 of
[`../../ng/impl_plan/psp_file_format.md`](../../ng/impl_plan/psp_file_format.md), branch
`ng-psp-encoding`. Design authority:
[`../../ng/spec/psp_file_format.md`](../../ng/spec/psp_file_format.md) §8.*

---

## 1. The step, and what was already true

**A record that straddles the rolling buffer is retried from its start with the running state
restored, and the buffer grows for a record larger than it.**

**The retry loop was built at D3, because a reader cannot work without one**, and its state is
restored by construction: `read_record_head` and `decode_record` are pure over a slice, and the
arm that answers a record's `Truncated` calls `pump` and nothing else. So — as at C3 — this step
could not find a bug, because there was none to find. **What it owes is the oracle**, and the
plan names it: *a decode forced to refill at every possible boundary*.

## 2. The oracle, and the first version of it proved nothing

A reader meets a file as a stream of compressed bytes, so the obvious reading of "every possible
boundary" is: hand the reader `n` bytes a read, for `n` from one to the whole file, and require
the same records every time. That sweep is here and it passes at all 837 schedules over its
fixture.

**It also retried a record exactly zero times.**

**zstd decodes in internal blocks and emits one whole**, so a payload that fits a single emission
is delivered in one piece however slowly its input arrived. Slowing the *input* moves when the
emission happens; it does not cut a record in half. A test that stopped there would have proved
the walk works and nothing at all about restarting it — the failure this milestone has now
produced five times, and the first time the oracle caught it about itself rather than a reviewer
catching it about me.

**What straddles a record is the buffer running out**, so the second sweep uses blocks larger
than the rolling buffer — which is what real data does at depth — and asserts, as part of the
test, that the schedules actually retried. Measured over 1,999 records in blocks of up to 210,894
bytes against a 16 kB buffer:

| bytes a read | retries |
|---:|---:|
| 1 | 58,778 |
| 2 | 29,395 |
| 3 | 19,601 |
| 17 | 3,469 |
| 251 | 246 |
| 1,024 | 70 |
| 16,384 | 16 |
| the whole file at once | 16 |

**Even the single-shot read retries sixteen times**, because a payload larger than the buffer
straddles it however fast the input arrives — which is the difference between this sweep and the
first one. The assertion demands more than a tenth of the record count, so a sweep that stopped
retrying fails rather than quietly passing.

**Seeing that at all needed the reader to say so.** `retries_after_a_refill` is a `#[cfg(test)]`
counter, because it is the one thing about a restartable parse that cannot be observed from
outside: a walk that comes out right is silent about whether the retry ever ran.

## 3. What the tests are

Four new ones, taking `ng::psp::block` from 74 to 78.

| test | what it forces |
|---|---|
| `a_decode_forced_to_refill_at_every_boundary_gives_the_same_records` | every source granularity from one byte to the whole file — 837 schedules — against a single-shot read |
| `a_decode_of_blocks_larger_than_the_buffer_is_retried_and_still_exact` | the same over blocks the buffer cannot hold, **with the retries counted and asserted** |
| `a_record_larger_than_the_buffer_survives_every_refill_schedule` | spec §8's "many alleles, many chain ids" record, at five granularities, and the buffer back to the budget afterwards |
| `a_refill_inside_a_block_head_is_retried` | a refill inside a block's own opening three fields, each made multi-byte on purpose |

## 4. Falsification — spec §8's own defect, and four more

| defect injected | tests failed of 78 |
|---|---|
| **the retry advances the coordinate before refilling** — spec §8's exact wording | 4 (it was **1** before this step) |
| the retry consumes the record before refilling | 5 |
| the buffer never grows | 3 |
| **the retry counter never rises** — the oracle's own witness | 1 |

The last is the one that matters most: it is what stops the second sweep passing on a schedule
that never retried, which is precisely how the first sweep was vacuous.

## 6. What D5 inherits

D5's oracle — restart equals sequential — already exists in one form
(`a_reader_starting_at_a_block_gets_the_tail_of_a_full_read`, D3). What it owes on top is the
same over a file where a running difference has somewhere to go wrong, and over the refill
schedules this step added: a block boundary and a buffer boundary are different things, and only
one of them is under the writer's control.
