# ng psp store — F0: a field's shape joins the manifest

*Implementation report, 2026-08-28. A step added to Milestone F of
[`../../ng/impl_plan/psp_file_format.md`](../../ng/impl_plan/psp_file_format.md) by the owner's
ruling of 2026-08-28, branch `ng-psp-encoding`. Design authority:
[`../../ng/spec/psp_file_format.md`](../../ng/spec/psp_file_format.md) §4.5.*

---

## 1. What the step is

**The manifest now carries all three things spec §4.5 asks it to carry for every field: the
name, the shape, and the encoding.** Until this step it carried two.

**⚠ Read this report against [the review](../reviews/ng_psp_f0_2026-08-28.md) and
[its fixes](../reviews/fixes_applied_ng_psp_f0_2026-08-28.md).** The review found one Blocker
and renamed the key: what is described below as *cardinality* is called **shape** in the code,
because `cardinality` is production's word for a different half of the same idea.

Spec §4.5:

> The header carries, for each field of a record: its name, its cardinality, its encoding, and
> that encoding's parameters.

`FieldSpec` had `name` and `encoding` only. The departure was recorded at A1
([that report](ng_psp_a1_a2_2026-08-26.md) §2.8), confirmed by the A1+A2 review, and carried
forward unanswered to Milestone F — because **from F a change to the manifest costs a format
version**, and before F no psp file existed to be incompatible with. The owner ruled on
2026-08-28: add it now.

## 2. Decisions taken here

### 2.1 What cardinality means here: how many values, not how often the field repeats

Two different things could be called a field's cardinality, and only one of them is in the file.

**In:** whether one of the field's values is a single value or a counted run of them. An
observation's read list is a count followed by that many identifiers; an allele's sequence is one
byte string, however long. This is the sense spec §4.5 attaches its promise to — *"a reader can
skip a field it does not recognise, provided the manifest says how to measure its length"* — and
the sense production's registry uses when it "distinguishes a column's cardinality from its
element type".

**Out:** how many times a field is repeated inside one record. Twelve of the body's twenty-two
fields are written more than once — ten once per observation, and two more once per witness run
inside an observation — and nothing in the manifest says so; a record's own counts do. Counted
against `encode_record_body`, not against the array's own comment, which said *nine of these
nineteen* and had been stale since the field list grew. That was already true and
is unchanged, and `BODY_FIELDS`' and `RecordLayout`'s doc comments now say which of the two
senses the manifest carries rather than saying it carries neither.

**A length-prefixed byte string is one value, not a list.** Its prefix counts its bytes, not how
many of the field a record holds.

### 2.2 The two accounts of a field's shape may not disagree

Every encoding already implies exactly one cardinality, so the key repeats something the file
already says. **A repeated fact that is allowed to differ from the original is worse than no
repetition**, because a reader then has to pick which to believe. So:

- `FieldEncoding::cardinality()` is the one place the pair is decided, an exhaustive match with
  no wildcard — a scheme added to the closed set has to say there how many values it lays down
  rather than inheriting *one* in silence.
- `check_cardinality` refuses a field whose two declarations disagree, and it runs on **both**
  sides: `Header::encode` refuses to write one (`InvalidHeaderField`) and `Header::decode`
  refuses to read one (`MalformedHeader`).
- `FieldSpec::new(name, encoding)` fills the cardinality from the encoding, and every field this
  build declares goes through it — so the one table describing a record cannot hold an
  inconsistent pair.

### 2.3 An unrecognised spelling is refused, not fallen back from

`cardinality_of` refuses a value that is not one of the two, rather than taking the encoding's
own answer. The fallback is the dangerous version: a later writer's `per-observation` field is
one this reader *cannot* step over, and quietly substituting `one-value` would step over it once
and resume in the middle of the next field — a plausible parse of the wrong bytes, which is the
failure class this format spends everything else avoiding.

### 2.4 The key is required, not defaulted

A field entry with no `cardinality` is refused. There is no psp file in existence that omits it,
so there is nothing to be compatible with, and a file that omits it was not written by anything
that agreed to this format.

### 2.5 The format version does not move

`FORMAT_VERSION` stays `(1, 0)`. **This is the last step where that is free**: no psp file exists
yet, which is exactly the owner's reason for taking the change now rather than later. The record
codec is untouched, so `the_fixture_encodes_to_these_exact_bytes` — the one assertion in
`record.rs` that does not come from the code it tests — is unchanged and was not regenerated.

**In the file.** One line per declared field, beside the two that were already there:

```toml
[[manifest.field]]
name = "observation-reads"
cardinality = "a-list"
encoding = "chain-id-list"
```

Twenty-five of the record's twenty-seven fields are `one-value`. The two lists are
`chain-id-changes` in the head and `observation-reads` in the body — the two halves of the
chain-id column, which are the only runs of values a record carries. That count is an assertion
(`exactly_two_of_the_records_fields_are_lists`), not a sentence.

## 4. Tests added

Seven, all in `header.rs`:

| test | what it pins |
|---|---|
| `every_scheme_round_trips_with_its_own_cardinality_and_is_refused_with_the_other` | all eight encodings, both ways: declared with the cardinality it lays down a file round-trips; declared with the other one it is refused, and the message names both |
| `a_file_whose_cardinality_disagrees_with_its_encoding_is_refused_by_the_reader` | the refusal reaches a **reader**, not only the writer — a hand-built header never goes through `encode` |
| `an_unknown_cardinality_is_refused_and_the_message_lists_the_known_ones` | `per-observation` is refused rather than substituted for |
| `a_field_that_declares_no_cardinality_is_refused` | the key is required, not defaulted |
| `the_header_text_names_each_fields_cardinality` | the key reaches the **bytes**, one line per field, read off the file's own text |
| `exactly_two_of_the_records_fields_are_lists` | 27 fields; `chain-id-changes` and `observation-reads` are the lists |
| `the_cardinality_list_holds_every_value_the_type_has` | the writer spells from the list the reader recognises from — the two-sided rule `ALL_ENCODINGS` already keeps |

**Six defects injected, six caught.** Each was applied to a clean copy of `header.rs`, the psp
suite run, and the failing tests counted. Described so that each can be reapplied from this
table alone — the scratch that produced them is not tracked:

| defect | tests that caught it |
|---|---|
| `check_cardinality` returns `Ok` before comparing | 2 |
| `cardinality_of` falls back to the encoding's own answer instead of refusing | 1 |
| the `AList` arm of `spelled()` returns `"one-value"` | 4 |
| `FieldEncoding::cardinality` returns `OneValue` for `ChainIdList` | 2 |
| `WireHeader::from` writes the literal `"one-value"` for every field | 3 |
| `#[serde(rename = "field-cardinality")]` on the wire field, affecting both directions | 6 |

**One of those found a weak test rather than a defect.** `the_header_text_names_each_fields_cardinality`
was written as a bare substring check and passed with the key renamed to `field-cardinality` —
because that name *ends in* the one being looked for. It is anchored at the start of a line now,
and it catches the rename.

## 6. Trade-offs and follow-ups

**The key is redundant with the encoding, and deliberately so.** Nothing a reader does depends on
it that the encoding could not already have told it; what it buys is the file saying its own
shape in the terms spec §4.5 fixes, and a refusal when the two say different things. The
alternative — deriving it and never writing it — was the state before this step, and the owner
ruled against it on 2026-08-28.

**What it still does not buy: a later writer's field that repeats once per observation.** §2.1
says why, and `RecordLayout`'s doc comment carries the consequence: such a file is *accepted* and
decoded into plausible nonsense from the second observation onwards. Nothing in the manifest can
refuse it, so a later writer adding one must raise the format version — which a reader does
refuse. That was true before this step and is unchanged by it.
