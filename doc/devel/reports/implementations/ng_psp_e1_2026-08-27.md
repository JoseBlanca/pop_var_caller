## 1. What the step is

**Which reads are live at a record, written as what changed since the last one.**

A chain id names the read that produced a piece of evidence, and since the owner's ruling of
2026-08-17 ng names every read it folds rather than only the ones that disagreed with the
reference — because the cohort merge has to tell a read that covered a position and agreed from a
read that never reached it. That makes this the field that decides the file's size at depth:
measured on real alignments, the ids are **16 % of the file at eleven reads a position and 89 % of
it at three hundred** (spec `psp_record_encoding.md` §6).

**A read of length L is named at every one of the L positions it covers**, so the whole-list form
stores each read about L times. This step stores only what changed: which ids started covering a
record and which stopped, with a reader carrying the set forward. The same measurement puts that
at **0.432 bytes a position at 11.4 reads against 1.020 for the whole list as raw identifiers, and
6.42 at 293 reads against 43.78** — 2.4 times smaller at the shallow corner and 6.8 at the deep
one. *⚠ This sentence gave 43.78 as the baseline for both corners, which reads as a hundredfold
saving at 11.4 reads; 1.020 is the shallow corner's, and the review measured it.*

## 2. Decisions taken here

### 2.1 A block's restatement is not a field — it is the reset

Spec §3.2 requires the live set to restart at every block, which is what lets a reader begin at
one. **`start_block` empties the set**, so a block's first record has nothing to depart and its
arrivals *are* the whole live set. There is no separate "here is the set" field to write, to
version, or to keep consistent with the changes that follow it.

The reset is one assignment over a `PerBlockState` struct holding the set, on both the writing and
the reading side — the shape `RecordEncoder` and `BlockCursor` carry theirs in, and **not `Copy`**,
because [the D4/D5 review](../reviews/ng_psp_d4d5_2026-08-27.md) measured what a `Copy` derive does
to the next person adding a collection: `error[E0204]` first, whose cheapest answer is to put the
field somewhere that compiles and never resets.

### 2.2 A departure is a position in the live set; an arrival is an identifier

Spec §4: *"departures reference ids already live and can be spelled as positions in the live set
rather than as ids."* An identifier runs into the millions and costs four varint bytes; a position
in a set of a few hundred costs one or two.

**The two never meet outside the codec.** `LiveSetChanges` holds identifiers on both sides, and the
conversion to and from positions happens only while bytes are being written or read — which is the
hazard arch §7 names by name: *"two `u64`s that must not be transposed"*.

### 2.3 ⚠ Departures are written first — and this section's reason for applying them early was wrong twice over

*What follows is the decision as taken. [The review](../reviews/ng_psp_e1_2026-08-27.md) found it a
**Blocker**, two agents independently; [the fix report](../reviews/fixes_applied_ng_psp_e1_2026-08-27.md)
§1 has what replaced it.*

The decision was: write the departures first and **apply them before the arrival count is read**,
so the set a position indexes is always the set as it stands at that moment.

**Both halves of that were untrue.** The departure loop had already finished before the apply, so
the positions were resolved against the pre-departure set either way — and `encode_changes`
binary-searches that same pre-departure set on the writing side. The eager apply bought nothing for
position resolution.

**What it cost was the retry.** Any buffer that stops in the arrival half returns `Truncated`,
whose contract is *fetch more bytes and re-parse this record from its first byte* — and the set had
already moved. Measured over a record that departs one read and gains one, five of its six cut
points retried to `Ok` with a read silently gone from the live set for the rest of the block.

**Now: decode the whole record, then apply it.** The wire format is unchanged, because both sides
already resolved a position against the set the previous record left. The order still matters, for
a different reason: an arrival is checked against that set, which the reader can only reach once it
has read the departures.

### 2.4 A run of ascending values costs its gaps, biased by one

Arrivals are ascending and distinct, and so are departure positions, so consecutive values differ
by at least one: each is written as `next - previous - 1`, the first absolutely. Identifiers are
allocated in order, so arrivals at a record are dense and a gap costs one byte.

### 2.5 The bytes are read through `record.rs`'s own reader, not a second one

`FieldReader` is `pub(super)` now. The line it draws — a field that ran out of bytes is
`Truncated` and a field that cannot mean what it says is `Malformed` — is what Milestone D's
restartable reader branches on, and a chain-id stream that drew it slightly differently would make
a streaming reader either reject a good record or retry for ever on a bad one. That is the C2
review's Blocker, and re-deriving the split here would have re-opened it.

**The public entry point takes a slice** and says how many bytes it used, rather than the module's
own byte cursor: where this stream sits inside a record is E3's question, and a signature that
assumed it would answer E3 early.

## 4. The oracle that would have been vacuous, and what it took

**A test that re-writes one block on its own and compares proves nothing about restarting.** The
defect spec §3.2 names is a difference that survives a block boundary *on both sides at once*: the
writer keeps the previous block's set and the reader carries its own forward to match, so a
sequential read is self-consistent and only a reader starting mid-file sees anything wrong. Two
freshly written files agree with each other under exactly that defect.

`a_block_read_alone_gives_the_sets_it_gives_in_the_middle_of_a_file` therefore writes **one** file
and reads it twice — once from the beginning, once from the second block's first record — and
compares both against the sets the writer was handed. Measured, the writer-side and reader-side
resets each fail it independently.

## 5. Falsification — ten defects injected

*⚠ Ten for ten, and the suite was still blind to one whole class: every one of these was a defect
in *what* the codec computes, and none touched *when* it computes it. The review's Blocker is in
the second class. The strengthened suite's table is in
[the fix report](../reviews/fixes_applied_ng_psp_e1_2026-08-27.md) §6 — fifteen defects, fifteen
caught.*

| defect injected | tests failed of 13 |
|---|---|
| the writer does not restart at a block | 2 |
| the reader does not restart at a block | 2 |
| a departure is written as its identifier, not its position | 7 |
| departures are never applied | 4 |
| departures are applied only after the arrivals are read | 4 |
| an arrival for a read already live is accepted | 1 |
| a departure position is not bounded by the live set | 1 |
| the ascending gap is not biased by one | 5 |
| a record naming the same id twice keeps both | 1 |
| a count no record could hold is believed (**each count separately**) | 1 each |

**Ten for ten — and the last row is why there are two of it.** The first version of the count test
used the arrivals only, and replacing the *departures*' bound with a plain varint read passed every
test in the module. Both counts are covered now.

## 6. What it costs, measured

`the_changes_cost_a_fraction_of_writing_every_record_s_list` builds 400 positions with three reads
starting at each and reads 100 bases long — about 300 live at once, the top of the committed depth
range — and compares against **the cheapest honest alternative rather than the naive one**: each
record's ids written as ascending varint gaps, which is spec §6's middle arm and the one that
captures 60 % to 86 % of the available saving on its own.

**3,257 bytes against 106,166 — 32.6 times smaller**, before compression. The assertion asks for a
factor of 16, so the fixture can change shape without becoming a number nobody re-measures.

*This is a fixture, not a corpus. The figures that decide the design are spec §6's, taken on real
alignments; this one says the implementation is in the same regime as the design it implements.*

## 8. What E2, E3 and E4 inherit

- **Re-entry is E2's, and nothing here assumes one stretch per id.** An id may go live, stop, and
  go live again — 83 % of ids on the human sample and 91 % on tomato — and arrivals and departures
  already express that. What E2 owes is a fixture that *contains* it on a real corpus and a test
  that counts it. **⚠ What this step owed and did not have was making the path reachable at all**:
  a returning id sorts *below* every id allocated since it left, and that is the only shape that
  makes either of this module's merges interleave. Every fixture allocated ids in walk order, so
  both interleaving arms were dead code under test — measured by replacing each with `panic!` and
  watching all 214 `ng::psp` tests stay green. Found by the review; there is a test now.
- **E3 is where the bytes go, and where the wiring can fail silently.** A writer that forgets
  `start_block` at a block boundary produces a file that is wrong from that block's first record
  and parses perfectly, because the reader restarts whether the writer did or not. The call site
  is E3's and so is the test that holds it.
- **E4's residual needs the count check spec §5 names**: a derived id list must be at most its
  observation's read count and at least half of it, since at most two mates share an id. The live
  set this step maintains is the minuend.
