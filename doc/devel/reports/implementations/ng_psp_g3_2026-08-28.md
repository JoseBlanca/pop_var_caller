# ng psp store — G3: replacing the trailer, and the write-side error causes

*Implementation report, 2026-08-28. Step G3 of
[`../../ng/impl_plan/psp_file_format.md`](../../ng/impl_plan/psp_file_format.md), branch
`ng-psp-encoding`. Design authority: [spec §6.5, §6.7, §3.4](../../ng/spec/psp_file_format.md),
[arch §4.2](../../ng/arch/psp_file_format.md).*

---

## 1. What the step is

**`replace_trailer(path, payload)` — rewriting a finished psp's closing payload without touching
its blocks or its index.**

It is the cheap operation, and the reason the index sits *before* the trailer (spec §3): the
trailer's offset is where the rewrite starts, so everything in front of it stays as it was. It
exists because the trailer is where things computed *after* the records land — the per-sample
summary today, whatever the statistical work adds later (spec §3.4).

**And the write-side error causes**, carried forward from the F3 and F4 reviews and assigned to
this step because G3 is where the writer's surface is the one being extended.

## 2. Decisions taken here

### 2.1 It reads the footer, and deliberately not the header or the index

Spec §6.7's table names exactly two refusals for this operation: **no valid footer**, and the
file's own bytes. So `replace_trailer` reads the fixed tail, adds the two rules that need the
file's length — that the sections end exactly where the footer begins, and that the index does
not start inside the header — and stops there.

Reading the block index too would cost an index decode per call, which is what "the cheap
operation" is against; and it could not make the file safer, because **every field written back
except the trailer's length is the file's own**. A footer with a wrong index offset is exactly as
wrong afterwards as before.

The two length-aware rules are repeated here rather than shared with `PspReader::open`, which
applies them in the same breath as reading the index and the header — the two things this
operation exists not to read.

### 2.2 The file is trimmed, and a shorter trailer is why

A reader takes the **last** 48 bytes of a file for its footer. Replacing a twenty-byte trailer
with a five-byte one and leaving the file at its old length would put fifteen bytes of the old
trailer past the new footer, and the reader would take the tail of a trailer for a footer and
refuse the file. `set_len` after the write is what stops that, and
`a_trailer_of_any_length_replaces_the_one_before_it` walks it through longer, shorter and empty.

### 2.3 The footer it is about to write is read back first

The obligation `finish` carries (F3 §2), for the same reason: a footer that reaches disk and is
then rejected has cost a file that was readable a moment earlier. It is one 48-byte decode.

### 2.4 A killed run and a foreign file get the same answer

`open` tells them apart, because only one can be fixed by re-running the pileup. Here both mean
the same thing — **there is no trailer to replace** — so both are `Incomplete`, and the head magic
is not read.

### 2.5 The write-side errors carry their causes

Five variants carried `reason: String` and nothing underneath. Now:

| variant | what it carries |
|---|---|
| `RecordRefused` | the `BlockWriteError` itself — one cause type, so no `reason` at all |
| `BlockRefused` | the `BlockCompressError` itself, likewise |
| `UnsupportedManifest` | a `ManifestRefusal`: the cut rule's error or the compressor's, which a caller could not tell apart from a sentence |
| `WouldNotBeReadable` | `reason` naming *which structure*, and an optional `NotReadable` — the index's, the footer's or a block head's own decoder error. `None` for the one rule the writer checks itself, the index's checksum against the footer's copy of it |
| `InvalidHeaderField` | **left as it was**, and this is a decision: three of its four sites are rules with no cause, and the fourth's cause is a `toml::ser::Error`. Carrying it would put `toml` in this crate's public error surface for one site |

**No `Display` repeats its own cause**, which is what the G1 review asked for: the parent names
what was being done and the chain says what was wrong with it.

## 4. Tests added

**Nine.** The three that carry the most:

**`replacing_a_trailer_leaves_the_blocks_and_the_index_byte_identical`** — spec §6.5's whole
claim, and compared **as bytes** rather than as a decode: an index that happened to decode the
same way after being rewritten would pass a weaker check. The records are then walked and compared
against the fixture.

**`a_trailer_of_any_length_replaces_the_one_before_it`** — longer, shorter, empty, and longer
again, each read back and each leaving a file whose sections end exactly where its footer begins.
The shorter case is the one §2.2 is about.

**`only_the_trailers_length_changes_in_the_footer`** — every other field of the footer is compared
field for field against the one before, by rebuilding the old footer from the new one with only
`trailer_bytes` restored. A rewrite that invented any of them fails here.

The rest: a file with no footer is `Incomplete`; a footer whose sections do not account for the
file is `Damaged`; a footer putting the index inside the header is refused **and the file is
unchanged afterwards**; a file that was never a psp is refused and left byte-identical; a missing
file names itself and what was being done to it; and replacing the same trailer twice gives the
same file length.

**Six defects injected, six caught**, every anchor asserted to match exactly once first:

| defect | caught by |
|---|---|
| the file's length is set past its end rather than to it | 4 |
| the rewrite starts at the index rather than the trailer | 4 |
| the footer keeps the old trailer length | 4 |
| the sections-account-for-the-file check is dropped | 1 |
| a killed run is reported as damage rather than incomplete | 1 |
| the index-inside-the-header check is dropped | 1 |

⚠ **The last of those survived the first run**, and the test that now catches it was written
because of it: nothing covered the one rule that stands between a footer with nonsense offsets and
a fresh footer blessing them.

⚠ **The first row's label was wrong when this was written**, and the G3 review caught it. The
mutation actually run set the file's length to `u64::MAX`, which four tests catch; the mutation
the label describes — *deleting* the `set_len` — is caught by one. Two true statements about two
different mutants, and the table claimed the second while running the first.

## 6. Trade-offs and follow-ups

- **⚠ A crash part-way through leaves a file every reader refuses, and the old trailer is
  already gone.** That is the right outcome — a half-written footer must not look finished — but
  it means this is not a safe in-place edit of a file whose *existing* trailer matters. Spec §6.4
  gives append the same warning and the same answer, and the doc comment repeats it: write to a
  new path and rename if that matters to the caller.
- **No test kills the process mid-rewrite.** The failure paths are covered by refusals before any
  byte is written; the interrupted-write case is H2's, where a writer is killed for real.
- **`replace_trailer` does not check the format version**, and spec §6.7's table is why — it does
  not list `UnsupportedVersion` for this operation. A file written by a newer format whose footer
  layout changed would fail `decode_footer` first; one whose footer is unchanged has a trailer this
  operation treats as opaque bytes, which is what the container says it is (spec §3.4).
