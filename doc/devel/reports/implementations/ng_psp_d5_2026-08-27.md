# ng psp store — D5: every running difference resets at a block boundary

*Implementation report, 2026-08-27. Step D5 of
[`../../ng/impl_plan/psp_file_format.md`](../../ng/impl_plan/psp_file_format.md), branch
`ng-psp-encoding`. Design authority:
[`../../ng/spec/psp_file_format.md`](../../ng/spec/psp_file_format.md) §3.2.*

---

## 1. The step, and the honest size of it

Spec §3.2: *"Every block is self-contained … **every running difference inside it restarts** — the
position difference, the coverage difference, the chain-id difference."* And: *"This is the
property goal 2 rests on, and the one most easily broken by accident. A block that fails to reset
a running difference reads back wrong from its first record — and plausibly wrong, because
coverage is smooth."*

**There is exactly one running difference today.** The position offset is it: the coverage
difference is the window's mean coverage, which ng computes nowhere (Milestone B1/B2 are blocked
for that reason), and the chain-id difference arrives at Milestone E. So this step, like C3, adds
no encoding and changes no bytes. **What it adds is the statement of the property in its strongest
form, for the differences that are coming.**

## 2. ⚠ And the property was already held — measured, not assumed

The defect this step exists to catch is a difference that survives a block boundary *on both
sides at once*, so a sequential read stays self-consistent and only a reader starting mid-file
sees anything wrong. That is the silent, plausible failure §3.2 names.

**I injected exactly that** — the writer keeps the previous block's coordinate as its base, and the
reader carries its own forward to match — and **eleven tests failed**, three of them this step's
and eight of them already there. The module's `walk` helper anchors every check to a block's
*declared* first position, so a great deal of the suite is implicitly a restart test.

So D5 is not closing a hole. It is putting the property where the next milestone will meet it, and
saying which tests carry it — which is worth a commit of its own for the reason the plan gives:
when the chain-id live set arrives, the person adding it needs to find this, not rediscover it.

## 3. What the three tests are

| test | the form of the property |
|---|---|
| `a_block_read_alone_gives_what_it_gives_in_the_middle_of_a_file` | **the strongest form**: a reader handed one block's bytes and nothing else has no history at all, so any difference still being measured from an earlier block shows as records at the wrong coordinates. Every block of a 108-record file over three contigs, compared against the same block read in the file |
| `restart_equals_sequential_from_every_block_at_every_refill_schedule` | the plan's own oracle, crossed with D4's: a block boundary and a buffer boundary are different things, and only one is under the writer's control. Five refill schedules × every block |
| `a_block_is_written_the_same_alone_as_it_is_after_other_blocks` | **the writer's half.** A reader that restarts correctly is no use if the block it restarts at was written against a coordinate only the previous block knew. Every block rebuilt from its own records and compared byte for byte |

**The fixture puts the blocks far apart** — cells 0, 7, 41 and 900 of three contigs — so a
difference that was not reset lands a record tens of millions of bases from where it belongs
rather than one base out. A fixture with adjacent blocks would make the same defect a small
coordinate error, which is the shape §3.2 warns still parses.

## 4. Falsification

## 6. What Milestone E inherits

- **The lone-block oracle is where a wrong live set will show.** E1 restates the chain-id live set
  at each block's start; a block that inherited one would read alone differently from how it reads
  in a file, which is what `a_block_read_alone_gives_what_it_gives_in_the_middle_of_a_file`
  compares.
- **The place to put the new difference is `BlockCursor`** on the reader and `PerBlockState` on the
  writer. A field added to either is a compile error at the reset — measured at D1 and D3.
