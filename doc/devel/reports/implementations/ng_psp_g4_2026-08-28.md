# ng psp store — G4: appending to a finished file

*Implementation report, 2026-08-28. Step G4 of
[`../../ng/impl_plan/psp_file_format.md`](../../ng/impl_plan/psp_file_format.md), branch
`ng-psp-encoding`. Design authority: [spec §6.4, §6.3](../../ng/spec/psp_file_format.md),
[arch §4.2](../../ng/arch/psp_file_format.md).*

---

## 1. What the step is

**`PspWriter::append(path)` — reopening a finished psp and adding records to it.**

The footer says where the blocks end, so appending is truncating at the index offset and carrying
on: the old index, trailer and footer are discarded, the header and every block stay where they
are, and `finish` writes a whole new index made of the entries that were already there and the
ones this writer adds.

**And the last two things Milestone F left owed**: the byte-accounting assertion in `finish`, and
the per-block copy `push` was making.

## 2. Decisions taken here

### 2.1 It opens the file as a reader first

`append` writes a fresh index and footer onto whatever it finds, so **a file the reader would
refuse must not be extended** — which is the lesson G3's review taught `replace_trailer` at the
cost of a Blocker. Here the index is needed anyway, so `PspReader::open` is the natural way in and
every check it makes comes free.

### 2.2 The manifest is checked before the file is walked, and the order is a finding

`BlockBuilder::from_manifest` is what refuses a record layout this build cannot write, and the
walk that finds the last record needs the same layout to *read*. Walking first made a manifest
this writer cannot honour arrive as a **reader's** refusal wrapped in `Reopen` — the wrong class
for the thing spec §6.4 calls out by name. Checking the manifest first puts it back in
`UnsupportedManifest`, and the test that found it asserts the class rather than "an error".

### 2.3 Coordinate order across the seam comes from the last block's heads

Spec §6.4: the first appended record must not precede the last one already in the file. The index
gives only each block's *first* position, so the last record's coordinate needs the last block —
and **only its heads**, which is what G2's selective walk is for. `BlockBuilder::continuing_after`
seeds the order check with it; a builder that started blank would accept a record behind the seam
and produce a file whose index no longer seeks.

**It seeds the order and nothing else.** No block is open, so the appended records start a new
block at the seam even when they fall in the grid cell the old last block covered — which is
legal, and is one of the two ways two blocks come to share a first position (`index.rs`), the
shape G1's Blocker was about.

### 2.4 It compresses at the level the file records

`create` writes `zstd-compression-level` into the header's parameters for exactly this reason
(F3), and `append` reads it back. An append at another level would put blocks in one file
compressed two ways with nothing saying so — goal 4 is that settings are recorded, and a setting
recorded and then ignored is worse than one not recorded.

### 2.5 The two things Milestone F left owed

- **The byte counter is checked against the footer** at the end of `finish`: the bytes written
  must equal the trailer's offset plus its length plus the footer. If they ever disagree, every
  offset the footer holds is measured from a different file than the one on disk.
- **The per-block copy is gone.** `compress` hands back a borrow of the compressor's own buffer,
  and copying it out was the price of borrowing `self` twice — one allocation the size of a
  compressed block, per block. The fields it needed are disjoint from the compressor's, and
  naming them says so to the borrow checker.

**The third owed item — splitting `PspWriter` into a file half and a builder half — is not done,
and writing `append` is the reason.** The argument for it was that "append reopens the same
machinery, so the split pays twice". It does not: `append` builds the same fields and then reuses
`push` and `finish` unchanged. What the split was to buy was the `Option<BlockBuilder>`, two
`expect`s and the per-block copy; **the copy is gone without it** — measured by the G4 review with
a counting allocator, 3 allocations of 4 kB or more across twenty block-closing pushes against 23
with the copy restored, which is exactly one per block.

⚠ **One sentence of that argument was wrong** and the review said so: the `Option<BlockBuilder>`
is *not* what makes "finished exactly once" a type-level fact — `finish(self)` is. The honest
framing is that the split is deferred into one function's borrow pattern, not that its case was
refuted; the case is weaker than it looked, and what is left of it is the two `expect`s.

## 4. Tests added

**Eight.** The three that carry the most:

**`an_appended_file_reads_back_as_one_file`** — the two record lists concatenated, compared field
for field against one walk. An append that lost the old records, or wrote the new ones somewhere a
walk does not reach, fails here rather than in a count.

**`appending_leaves_the_header_and_the_old_blocks_untouched`** — the bytes before the old index
offset are compared **as bytes**, the old index entries come back unchanged, and the first
appended block starts exactly where the old index did.

**`a_record_that_precedes_the_seam_is_refused`** — both halves of the order rule, on the position
and on the contig. A builder that started blank would accept both; the seed from the last block's
heads is the only thing that makes it fail.

The rest: a record at exactly the seam's own position is **accepted**, because the rule is *must
not precede* and two records may begin on one base; a file with no footer cannot be appended to;
an append is refused on a manifest this writer cannot honour, **with the file left byte-identical**;
an append dropped before finishing leaves a file every reader refuses; and an append compresses at
the level the file records.

⚠ **The level test's first fixture could not fail.** It compared an appended block against a fresh
block at the level the file records — which *is* this build's — so an append that ignored the
record entirely passed. The file's recorded level is now patched to 1 in its own header text (one
character wide, so no offset in the file moves), the payload is varied enough that 1 and 9 differ,
and **both halves are asserted**: that the levels separate, and that the appended block is the
recorded level's.

**Eight defects injected, seven caught and one that cannot be** — the table has seven rows and
the eighth is the last paragraph:

| defect | caught by |
|---|---|
| the old index entries are dropped | 3 |
| the byte counter restarts at zero | 4 |
| the file is not truncated at the index | 6 |
| the seam's order is not seeded | 1 |
| the seam seed is stored and ignored | 1 |
| the file's own compression level is ignored | 1 |
| a fifth section is written between the trailer and the footer | 82 |

⚠ **The eighth is removing the byte-accounting assertion itself, and it survives — which is what
an assertion is.** It is visible only when a defect is present, and the fifth-section row is that
measurement: **82 tests fail with the assertion and 66 without it**, so it accounts for sixteen of
them. **The claim in the first version of this report — that the defect fails the same number
either way — was wrong**, and the G4 review caught it; the assertion is worth more than it was
given credit for, not less. It is kept because the sixteen include the one that fails at the
**writer**, naming the disagreement, rather than at sixty-six readers.

⚠ **And F's own figure for it, still in the code comment when this was written, was 1 failing
test against 7** — measured on a suite a third this size. A number measured on another tree is not
a fact about this one.

## 6. Trade-offs and follow-ups

- **⚠ An append loses the trailer the file had**, with the index it followed, and it is gone from
  the moment the file is truncated. Spec §6.4 says so and the doc comment repeats it: write to a
  new path and rename if that matters to the caller.
- **`WriteStats::records` counts what this writer wrote, not what the file holds.** The records
  already there were never counted by anything; the blocks they are in are in the index this
  writer inherited, so `blocks` *does* count both.
- **An append does not re-cut the block it lands beside.** A record appended into the grid cell
  the old last block covered opens a second block for that cell rather than extending the first —
  which is legal and, at a seam per append, cheap. A file appended to a thousand times would carry
  a thousand short blocks.
- **`PspReader::open` is paid in full on the way in** — the footer, the whole index and the
  header. That is the price of not extending a file a reader would refuse, and it is once per
  append.
