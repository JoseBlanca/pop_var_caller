# ng psp store — F1: the block index's own bytes

*Implementation report, 2026-08-28. Step F1 of
[`../../ng/impl_plan/psp_file_format.md`](../../ng/impl_plan/psp_file_format.md), branch
`ng-psp-encoding`. Design authority: [arch §3.4](../../ng/arch/psp_file_format.md),
[spec §3.3](../../ng/spec/psp_file_format.md).*

---

## 1. What the step is

**The index goes to bytes and back: one entry per block, in genomic order, so a reader can start
at any block without reading what comes before it.** `BlockIndexEntry` existed as a type from
A1; this is its codec, its checksum, and the refusals that keep a seek honest.

An entry is a contig, a first position and a byte offset. Nothing else — spec §3.3 removed the
per-block variation summary, because at a 100 kb block essentially every block holds something
that varies, so the field never said *skip*.

## 2. Decisions taken here

### 2.1 Two varints and a fixed offset, following production

Contig and position are LEB128; the offset is eight little-endian bytes. That is production's
split ([`src/psp/index.rs`](../../../../src/psp/index.rs)) and the plan's *reuse over rewrite*
rule points at it. The reasoning carries: contig numbers and positions are small in most files
and cost one to three bytes, while an offset is large and arbitrary, so a varint would usually
cost the same eight bytes and sometimes nine.

**Measured on the fixture:** an entry at contig 0, position 1 is **10 bytes**; at position
100,001 it is **12**, because that position needs three varint bytes. The layout is pinned
against a literal in `one_entry_encodes_to_these_exact_bytes` — 11 bytes for contig 3, position
300, offset 4,096 — so it is stated once outside the decoder that reads it.

**The index is not compressed.** It is read whole at open before any block is touched, and spec
§3.3 puts a whole genome at roughly 14,000 entries, a few hundred kilobytes paid once per open
sample.

### 2.2 The order is checked here, which production leaves to a caller

Production's `decode_index` says coordinate monotonicity is "the reader's responsibility (one
layer up)". **ng checks it in the decoder**, because of what the failure looks like: every use
of this index is a search for the block holding a coordinate, and on entries that are not
ordered that search *does not fail* — it returns the wrong block, and the records that come back
are a real sample's records from the wrong place. One comparison per entry, once per open file.

### 2.3 Positions may repeat; offsets may not — and that was measured, not assumed

The rule is **non-decreasing positions with strictly increasing offsets**, and the asymmetry is
forced by the writer rather than chosen.

A block closed early by the byte ceiling is followed by one that starts at the next record, and
two records may begin on the same base — a repeat tract and a generic locus do, and
`BlockBuilder::check_order` allows it deliberately. **Probed against `BlockBuilder` before the
rule was written**: with a one-byte ceiling and two records both starting at position 500, the
closed block and the next one both report `first_position = 500`. A rule demanding strictly
increasing positions would have refused a file this writer produces.

So it is the **offsets** that say two entries are two blocks: two entries at one offset are one
block indexed twice, and an offset that goes backwards points a seek behind where it has
already read.

### 2.4 The block count is bounded before it sizes anything

`expected_blocks` comes from the footer, which on a damaged file is as damaged as everything
else. The reservation is capped against what the buffer could actually hold.

**Measured by removing the cap:** a footer claiming `u64::MAX` blocks reserves that many
`BlockIndexEntry` at **24 bytes each**, and the decode dies inside `Vec::with_capacity` with
`capacity overflow`. **That is a panic on a damaged file**, which this module does not do — a
corrupt psp is data a run was handed, not a bug. So the cap keeps a hostile tail an *error*
rather than a crash; the memory is the lesser half of it.

*(An earlier draft of that comment said 16 bytes an entry and claimed the process aborts. Both
were wrong and neither had been run.)*

### 2.5 A path-free error, for F4 to dress

`IndexDecodeError` carries no file path, like this module's other codec errors
(`RecordDecodeError`, `BlockHeadDecodeError`): the file's name belongs to whoever opened the
file, and F4's `open` is what turns one of these into a `PspReadError`. Every variant means *the
file is damaged, rebuild it*; none is something a caller fixes by changing a setting.

**A contig number too large for a `ContigId` is refused, not truncated** — a wrapped number
names a real contig, so the seek would succeed and land on the wrong chromosome.

### 2.6 The checksum is production's function, called rather than copied

`checksum_index` delegates to `crate::psp::index::checksum_index`: XXH3-64 truncated to its low
32 bits, the same truncation zstd uses for its own frame checksum. Sharing it means there is one
XXH3 in the codebase rather than two that could differ. The index is the one region of a psp no
zstd frame checksum covers, which is why it carries one at all.

| `one_entry_encodes_to_these_exact_bytes` | the layout, stated outside the decoder that reads it |

**Eight defects injected, seven caught; the eighth was a bad mutation of mine, and the real one
it stood for is caught.**

| defect | caught by |
|---|---|
| the position order check is dropped | 1 |
| the offset check admits equal offsets | 1 |
| the offset check is dropped | 1 |
| trailing bytes are ignored | 1 |
| a contig number is truncated to `u32` instead of refused | 1 |
| the offset is written big-endian | 5 |
| contig and position are written the other way round | 5 |
| the reservation is unbounded (`Vec::new()` in place of the capped `with_capacity`) | **0 — and it changes no behaviour**, because `Vec::new()` over-allocates nothing either. The mutation that expresses the actual hazard is `Vec::with_capacity(expected_blocks as usize)`, and that one **is** caught, by `a_block_count_from_a_damaged_footer_does_not_size_the_allocation` |

The eighth is recorded rather than dropped because it is the trap the review process names: a
mutant that takes the same path on every input is not evidence about a test, and reporting one
as a survivor sends the next reader to defend a hazard that does not exist.

## 6. Trade-offs and follow-ups

- **Nothing checks an offset against the file's size**, because nothing here knows it. An entry
  pointing past the end of the file is F4's to refuse, at `open`, where the length is known.
- **`PspReadError` has no variant for a damaged index yet.** F4 adds it when it wires `open`;
  folding one of these into `CorruptBlock` would be the mistake the C1 review warned about,
  since that variant names a block and takes an `io::Error` as its cause.
- **The index is decoded whole and kept whole**, which is the design (spec §3.3) rather than an
  omission: a whole genome is roughly 14,000 entries, and the coarse-index-and-chain scheme
  `run_streaming.md` §7.2 asks for must not be built.
